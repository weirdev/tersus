## Interpreter flow

The Haskell implementation has two main execution paths after parsing:

1. `Parse.parseStatementBlock` converts source text into the AST types in `TersusTypes`. The parser remembers the structs and enums declared so far, so a `match` becomes an `if` chain of `Is` tests (the last variant in the final `else`, its pattern fields read with `Project`), `x is V` the application of `Is V`, `x as V` the application of `Cast V` (whose input contract is `x is V`, and which returns its argument), a variant literal the application of its `Ctor` (named `Enum::Variant`), and a struct literal becomes the application of a `Ctor` builtin to the fields in declaration order, and `x.f` the application of `Field f`; the checker, evaluator and proof engine see structs as ordinary builtin applications. `//` line comments are skipped as whitespace.
2. `TypeCheck.typeCheck` (and `elaborate`, which also resolves each `shrinks` clause by type) infers and checks types (unification inside a function body, with the declared parameter and return types and the builtin signatures), and `Proof.validate` runs it before validating. `Proof.evaluate` does not check types, since the CLI validates first.
3. `Proof.evaluate` executes statements concretely with a `State` containing lexical scopes plus the standard library value context. Assignments evaluate expressions and update bindings, `return` writes the top-level return slot and ends the program or function body (the remaining statements are dropped), blocks push a child scope, function calls run a native body or builtin (and must pass exactly as many arguments as the function has parameters), and validation statements are skipped. `if` runs the chosen branch as a block, and `while` runs its body as a block and then puts itself back at the front of the remaining statements until the condition is false. Nothing bounds evaluation, so a loop that never ends never returns.
4. `Proof.validate` symbolically validates the same statements with a `VState`. Runtime values are represented by fresh iotas, assignments add equality proofs, function calls whose arguments are all known are also evaluated for their result, with a budget of `validationFuel` statements so validation cannot hang on a long or endless callee, and check input contracts and instantiate exported output proofs (tied to the caller's variables by equalities between each argument's fresh iota and the variable, or the literal when the argument is one and the output contract mentions it, so a contract like `push`'s `size(return) = size(list) + 1` or `set`'s `size(return) = size(list)` is usable), `axiom` and `proof` declarations register validation-only rewrite rules, `affirm` asks the internal `ProofEngine` whether a proof is entailed by the current context (validation is a bounded search that is sound but incomplete: what it cannot prove is rejected as `Could not prove: P`, and the program adds `affirm`s, `define`s and `rewrite`s until it can, see LANGUAGE.md; `*` and `/` bind tighter than the other infix operators, and `/` must have a divisor proved non-zero; a failure reports the proof in source syntax, rendered by `Pretty.renderVarProof`) (a congruence closure over the known equalities, so equal arguments give equal results without any rewriting, plus difference constraints over its classes for integer comparisons, so `s = 3` gives `s > 0` and `i < n` gives `i + 1 <= n` (`x != y` facts and `c * x` terms are folded in by `refine` in `arithmeticEdges`, which adds edges the graph so far implies: `x <= y` with `x != y` is `x < y`, and `x - y <= d` is `c * x - c * y <= c * d`); the closure is built from use lists (`Closure`), and a `Solver` of the visible facts is kept in the state (`FactCache`): the places that add facts add them to it too, and a question uses it only when every fact it holds is still visible, adding the facts it lacks, so a long program does not intern every fact again at each `affirm`), and `rewrite` applies primitive or user-defined rules to expand that context (applying a rule only adds its outputs, with no `refl` copy of the other facts). A `forall` is a proof form `Forall index guards body` whose index is a `BVar`, interned as one term in the closure; `entailsAll` proves a `forall` goal for a fresh index meeting the guards, and instantiates `forall` facts at the `get(L, t)` terms it finds (`forallInstances`). `push` and `set` also export `return = push(list, x)` or `set(list, index, x)`, which the standard library rules `pushKeeps`, `setKeeps` use to say a given index is unchanged. `if` validates each branch from the state after the condition with the condition (or its negation) assumed, then joins them (`joinBranches`) by keeping only the facts both branches establish about the variables they assign. The candidates are the then-branch's facts (checked in the else-branch with the full engine) and, checked in both branches with `Engine.entailsDirect`, the proofs the program is about to need: the `affirm`s and loop invariants still to run (`upcomingProofs`, read from the continuations of the block and the blocks around it), the invariant and variant check of the loop body being validated (`withLoopEnd` keeps them in the rule context under a name no program can write), the facts from before the `if` rewritten to the new values of the variables it assigns, and the else-branch's facts. `while` checks its invariant on entry, treats the variables its body assigns as unknown, checks the invariant is preserved, and afterwards assumes the invariant and the negated condition. An `if` with a `return` in a branch cannot be joined, since the statements after it do not run on the path that returned. Instead each branch is validated followed by the rest of the program (`valReturningIf`), and the two ends are joined by keeping the facts both establish and merging the return values (`joinReturnPaths`). A `while` whose body contains `return` works the same way (`valReturningWhile`): the body is validated as a path that ends in a `LoopEnd` statement checking the invariant and the variant (such paths only go back to the condition, so joins ignore them), and the program after the loop is the other path, starting from the state where the condition is false. `for i in lo..hi` has no node of its own: the parser (`forStatement`) turns it into assignments of `lo`, `hi` and `i` (the first two to variables named `$lo i` and `$hi i`, which `Pretty` shows as `(start of for i)` and `(end of for i)`) and a `While` over `i < hi` with `i >= lo` and `i <= hi` ahead of the program's own invariant, `shrinks hi - i`, and `i = i + 1` after the body. `for x in list` and `for i, x in list` are the same loop over `0..size(list)` with a hidden copy of the list and `Let x (get(list, i))` at the start of the body (`elementLoop`); the copy (`$list L:C`) and the index when there is no `i` (`$index L:C`) are named by the line and column of the `for`, so loops that nest or follow each other with the same names do not share them. Loops also get inferred invariants (`inferInvariants`): candidates from the entry values of the variables the body assigns (`Engine.constantValues` gives the constants), and comparisons with the variables the loop leaves alone that `Engine.entailsDirect` (congruence and arithmetic only, no forall) says already hold; a body without a `return` is validated with the survivors assumed and every candidate it does not preserve dropped at once (`houdini`), and one with a `return` is validated up to its loop-back (`returningBodyPath`) and the candidate its error names is dropped (`dropByError`); if the loop is refused with an error that names an inferred invariant, `valWhileStatement` validates it again without, so errors are about the program's own invariant. A loop has to say how it ends, with `shrinks e` or `~` (the `Termination` of `While` and of `NativeFunct`; a loop without one is rejected by `loopTermination`). The type checker resolves `shrinks e` by the type of `e` (`elaborate`, which `validate` runs and which hands the validator the program with the clause rewritten): an `Int` becomes `Counting` (at least 0 when an iteration starts, smaller when it ends) and an enum or struct becomes `Parts` (replaced by a field of itself), and the validator never sees `Shrinks`. `startIteration` checks the variant is bounded below in the state where the invariant and condition hold and keeps its value in a variable named from the next iota; the check that it got smaller is a pair of validation statements (`smallerThan`) run at the end of the body, or in `LoopEnd` when the body has a `return`. A function with a clause does the same at its start (`startFunctionVariant`, variable `variant at entry`), and the copy of the function that its own body calls is marked `Recursing`, so `callTermination` knows a call is recursive and checks the variant of the arguments against the entry one (`valFunctInput` run on the callee's parameters). Whether code is guaranteed to terminate is not a fact of the state but an error at the source: `markFunctionBody` puts `$terminates` in the global context of every function that is not `~`, and a loop or call that may not end (`noteDivergence`) is rejected when that is present and the facts are not contradictory (`unreachable`). A smaller `shrinks` value is the internal builtin `Within`, entailed when the engine finds the first term among the field reads of the second (`partOf`), and a comparison of differences `x - y` with zero or with each other is turned into one of their sides (`differenceEntails`), since the difference constraints say nothing about the difference as a term. What the graph cannot decide goes to `Linear` (`linearSystem` turns the facts into equations and inequalities between the classes: `t = a + b`, `t = c * a`, `c * t <= a <= c * t + c - 1` for `t = a / c`, `size(l) >= 0`, and the relations; `linearEntails` asks whether they have a whole-number solution together with the negated goal): Gaussian elimination of the equations, rounding of each inequality's constant, then Fourier-Motzkin elimination (given up on past 300 constraints), only when some fact has an operation the graph cannot take. `inferInvariants` also proposes `a + b = n` for two loop variables and a variable the loop leaves alone.

The CLI in `app/Main.hs` drives these paths over a source file (logic in `src/Cli.hs`):

- `stack run -- check <file>` parses and validates the program, printing `OK` on success.
- `stack run -- run <file>` validates the program, and only if that succeeds evaluates it and prints its return value (nothing is printed when the program does not `return`).
- Use `-` as the file to read the program from standard input.
- Errors go to standard error, prefixed with `Parse error:`, `Validation failed:` or `Evaluation failed:`. The exit code is 1 for a failed program and 2 for bad command-line usage.

Next steps, roughly in priority order:
1. Element-level facts about lists (mostly done)
    `forall j in lo..hi: P` is implemented (see LANGUAGE.md): it is a proof form `Forall index guards body` whose index is a `BVar`, proved for a fresh index and instantiated at the `get(L, t)` terms of the closure, and `push`/`set` export frame foralls, so `examples/parallel_sum.tersus` states that each result element is the sum of its pair
    Instances come only from `get(L, j)` terms in the body, so a body that does not read elements is never used; `exists` is not implemented; and `forall` does not nest
    Proving a `forall` splits cases on the guards that kept an instance of a known forall from being used (`entailsBlocked`), up to `maxSplitDepth` levels and `maxSplitAttempts` entailments, then on the indexes the program reads (`maxSplitIndexes`). The splits commit to the guard that bears most on the goal (`maxSplitGuards`) and go deep (`maxSplitDepth`), which proves that a push and two sets keep `prev` and `next` in agreement in a doubly linked list (examples/linked_list.tersus, under a second) and rejects the broken variants in a few seconds. A forall is instantiated only at indexes of a low generation (`maxIndexGeneration`): those of the facts and the goal count 0, and the terms of an instance one more than its index, so an agreement forall does not feed itself. Each case split starts from the saturation of the case before it, and a saturation keeps its congruence closure (`Solver`), so a branch only adds the facts of its case
    `entailsAll` on large contexts is benchmarked in item 13: `frame_facts.tersus` takes 0.03s, and a program of N pushes with an `affirm` after each takes 0.06s at N=20 and 0.3s at N=40. An `affirm` that the facts already entail stops before any forall is instantiated

    Benchmarked at `-O1` on programs of N `push` calls followed by one `affirm`: N=20 takes 0.05s, N=40 0.2s, N=80 0.9s and N=160 7s (from 0.12s, 0.45s, 2.5s and 15s before this change, and 1.1s, 9.5s and over 80s before the closure was indexed).     The solver cache (`FactCache` in the state, see the interpreter flow) is dropped when a block ends, so the facts are interned again after an `if` or a `while`; keep the parent's cache beside the child's
    The union-find has no path compression, and constants without a key (user functions) are found by a linear scan
    The context carries the standard library facts twice inside a function body
14. Termination proofs written in the validation language (the clause today is `shrinks e` or `~`, see LANGUAGE.md, Termination)
    `shrinks e` is meant to become sugar for a block of `affirm`s, in the style of proof rules and loop invariants, about the state at the start of an iteration or call and the state at its end (what is bounded, what is smaller). `elaborate` already resolves it by type into `Counting` or `Parts`, which the validator checks with `boundedBelow` and `smallerThan`; those would become the expansion
    Needs obligations that relate two states, which the contracts do not have yet: the start state of an iteration or call has to be nameable at its end. The saved variant (`variant at entry`, and the hidden variable of a loop) is the special case of that
    Then a lexicographic pair, a list that loses an element, and mutual recursion can be written by the program, instead of being refused or declared `~`
