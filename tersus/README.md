## Validator written in Tersus

`lib/validation.tersus` starts a Tersus implementation of validation alongside the
Haskell implementation, which remains the bootstrap and reference. Its first
query, `hasEquality`, treats integers as symbolic value identifiers and proves
reflexive, symmetric and transitive consequences of the supplied equalities.
`hasCongruence` additionally closes equalities over binary applications of
uninterpreted operators, including nested applications. The host must give each
term a unique identifier and distinguish different operators.
`hasApplicationEquality` accepts applications of any arity and treats the
function as a term, so equal functions applied to equal arguments are equal.
`hasApplicationOrder` uses those equalities while following comparisons. A false answer
means only that the query did not find a proof. General proof terms and MIR
validation remain incomplete, and the production pipeline still uses Haskell.

`hasStrictOrder` follows strict comparisons transitively and substitutes
equivalent identifiers at either end of a comparison. `hasOrder` also handles
chains mixing strict and non-strict comparisons. Neither query handles
general arithmetic expressions. `hasDifference` follows difference constraints
with checked 64-bit intermediate bounds, giving up on a path if a bound would
overflow; it does not detect negative cycles. `entailsApplicationOrder` detects contradictions
formed by a cycle containing a strict comparison and treats those premises as
inconsistent. `entailsApplicationDisequality` transports explicit disequalities
through equality, uses strict comparisons, and detects an equality contradicting
a disequality. `entailsRefinedOrder` also strengthens a non-strict bound to a
strict one when its endpoints are known to differ. Other forms of contradiction
are not yet covered.

`entailsGoal` combines these facts in a proof context. `SelfHostedProof` interns
Haskell proof terms and runs supported relation queries against that context;
it declines unsupported goals and omits unsupported premises. It is a bridge
for comparison with the Haskell engine, not the production validation path.
The Tersus search is incomplete, so a negative answer does not establish that
the goal is false.

`validateProofSteps` checks a sequence of obligations in order. Its `Known`
steps are reserved for trusted premises and facts established by an operation;
an assertion must be a `Check`. The result identifies the first unproved check.
`validateExecution` also tracks local bindings and checks acyclic paths
independently. `SelfHostedMir.validateMirSubset` translates a limited subset of
typed MIR (copies, boxing, plain structs, pure binary operations, list and
array literals, empty and repeated-element arrays, length, indexed reads and updates,
first, last and list removal with known length, list append, assertions, jumps
and branches) to that representation. Reads require proof of their bounds, and literal sequence
elements have their known values. Append records the new length and element and
preserves previously checked reads; removal preserves known reads within the
shortened length. Simple relational invariants on non-generic structs are
checked at construction and assumed for typed values; enums are not yet
supported. It also checks a canonical single-block loop by proving
its declared invariant and an integer or fixed-limit countdown variant. Other
loop shapes and operations it cannot translate return unsupported. Functions
are checked with symbolic parameters and simple relational input and output
contracts. Direct calls to previously defined functions check those contracts
when the callee does not reassign its parameters. Contract assumptions support
total expressions; assumptions with operations requiring safety checks, other
calls and termination clauses remain unsupported. It
is used for comparison, not for production validation;
the returned flow state is one path's state and is not a joined postcondition.
Branch facts include both the boolean result and, for a saved comparison, the
relation between its operands at the time it was evaluated. A check of a boolean
term against a literal is discharged from the comparison that produced the term,
so `below = true` follows from `below` being `x < 6` with `x < 6` known.
The symbolic executor records multiplication by zero or one, division by one,
and concrete products, quotients and remainders when they fit in a signed
64-bit integer.

`MirEval.runNamedFunction` lets the host invoke a lowered Tersus function with
explicit MIR values. It executes code without checking its input contract or
the types and invariants of host-supplied values; the host must establish these
before calling it. The regression test validates the Tersus implementation with
the existing validator and compares its answers against `ProofEngine` for every
undirected equality graph of four identifiers, plus reversed and duplicate facts.
Future work needs an encoding of MIR and proof state, richer reasoning and
differential tests before the new validator can replace `MirValidate`.

## Interpreter flow

The Haskell implementation parses to the AST, checks its types, lowers it to the MIR, validates the MIR, and runs it (the stages are chained by `Pipeline`, which type checks the program once; steps 1 to 6 below):

1. `Pipeline.parseSource` puts the prelude (`lib/prelude.tersus`, embedded by `PreludeSource`: the traits `Sequence`, `Growable`, `Clone` and `Copy`) in front of a program that mentions any of those names and does not declare it, and `lib/string.tersus` (the struct `String`, with `print`) after it for a program that writes a string literal or mentions `String` (`Pipeline.libraries`; `Parse.stringLiteral` reads `"text"` as a struct literal of `String` with the UTF-8 bytes of the text), by parsing the prelude first and the program with the declarations it made (`parseStatementBlockWith`), so line numbers are the program's. The program itself is parsed with the places of its statements kept (`Parse.locating`): a `Mark line column` statement comes before each statement of a block (`Parse.located`), which nothing runs and the lowering reads as the place of the statements after it. `Parse.parseStatementBlock` converts source text into the AST types in `TersusTypes`. The parser remembers the structs and enums declared so far, so a `match` becomes an `if` chain of `Is` tests (the last variant in the final `else`, its pattern fields read with `Project`), `x is V` the application of `Is V`, `x as V` the application of `Cast V` (whose input contract is `x is V`, and which returns its argument), a variant literal the application of its `Ctor` (named `Enum::Variant`), and a struct literal becomes the application of a `Ctor` builtin to the fields in declaration order, and `x.f` the application of `Field f`; the checker, evaluator and proof engine see structs as ordinary builtin applications. `//` line comments are skipped as whitespace. A call written as a statement (`f(x);`, `s.print();`) is an `Assign` to a name that no program can write (`$call L:C`, `callStatement`), so its result is not used. `Cli.runSourceWith input Interpret` gives the standard input (`readInputBytes`, as bytes) to `readByte` and prints what the program wrote with `writeByte` (`MirEval.runProgramWith`, decoded as UTF-8) before the value it returns. `for i in lo..hi` has no node of its own: the parser (`forStatement`) turns it into assignments of `lo`, `hi` and `i` (the first two to variables named `$lo i` and `$hi i`, which `Pretty` shows as `(start of for i)` and `(end of for i)`) and a `While` over `i < hi` with `i >= lo` and `i <= hi` ahead of the program's own invariant, `shrinks hi - i`, and `i = i + 1` after the body. `for x in list` and `for i, x in list` are the same loop over `0..size(list)` with a hidden copy of the list and `Let x (get(list, i))` at the start of the body (`elementLoop`); the copy (`$list L:C`) and the index when there is no `i` (`$index L:C`) are named by the line and column of the `for`, so loops that nest or follow each other with the same names do not share them. `#[1, 2]` is the application of `ArrayFrom` to the list of its elements (a conversion that does nothing when it runs), and `Array<T, N>` the type `TArray T N`. `trait Name { fn f(...) -> T [{ in }] [{ out }]; }` is a `TraitDef`, and `impl Type { fn ... }` or `impl Trait for Type { ... }` an `ImplDef` that holds the functions it defines under the names `Type::f`; The functions of an impl are named `<Type>::f` or `<Type as Trait>::f` (`implFunctionName`); `Self` is read as the type of the impl (`declSelf`), and stays `Self` in a trait. `x.f(a)` is `F (Var ".f") [x, a]` until the checker knows the type of `x`, `Trait::f(x)` and `Type::f(x)` are calls of a name with `::` in it, and `<Type as Trait>::f(x)` a call of the function by its full name. `impl<T> Vec<T> { ... }` names the parameters of the impl after `impl` (`declImplParams`): every function of it gets them after its own type and size parameters, `Self` is read as the instance name of the struct with them (`Vec<'T>`, in `declSelf`, with the struct's fields registered under that name while the impl is read), and `Self::f` is the function of the base struct (`selfBase`).
2. `TypeCheck.elaborate` infers and checks types (unification inside a function body, with the declared parameter and return types and the builtin signatures) and resolves each `shrinks` clause by the type of its expression: an `Int` becomes `Counting` (at least 0 when an iteration starts, smaller when it ends) and an enum or struct becomes `Parts` (replaced by a field of itself), so the validator never sees `Shrinks`. The program is checked once, and the returns at the top level of a program have one type. It also takes traits and impls apart (`checkTrait`, `checkImpl`): a trait's types and contracts are checked with `Self` as a type with no fields; an impl's functions are checked as definitions at the top; for a trait impl they are compared with the trait's signatures with `Self` replaced, and for each trait function the checker adds a function named `Trait for Type::f` that has the trait's contracts and calls `Type::f` (`implCheckName`), so that the validator proves the impl meets the trait with no new reasoning (`MirValidate.inImplCheck` says which impl a failure belongs to). `inferExprR` gives back each expression with `x.f(a)`, `Type::f(a)` and `Trait::f(x)` replaced by the call of the impl's function (`resolveAssociated` looks `f` up among the impls of the type, in `tcAssoc`, and refuses a name that several define) for the type of `x` (or of the trait's `Self` argument), so nothing after the checker sees a trait, an impl or a method. `size`, `first`, `last`, `get` and `set` take a list or an array: `checkBuiltinCall` types the call from the kind of its first argument (and MirLower does the same when it replays the checker), so the validator and the later passes see one `Size`, one `Get` and one `Set` whatever the container, and an array's facts are a list's. `array(n, x)` needs a `n` that `constantInt` can fold to a number, which becomes the size in the type and replaces the argument, and an array may hold only `Int`, `Bool` and arrays (`plainElement`) and since it is held inline it can be a field of a struct or an enum and an element of a list (the native code lays out a field by the words of its type and a list by a stride of words, which the runtime also walks to clone, free, compare and print). The validator gets the size of every array local from its type (`MirValidate.withTypeFacts`: at a parameter, an assignment, a call result and a loop head), so no contract has to say it. `Box<T>` (a struct or an enum held in a Box) has the value of what it holds: `Box::new(x)` and `Box::unbox(b)` become the MIR's `MakeBox` and `Unbox`, which the validator, the executor and the proof engine treat as the same value, a Box is looked into where a struct or an enum is (`fieldType`, `readField`, and the `is`, `as` and projection builtins by `checkBuiltinCall`), and `checkFinite` refuses a struct or enum that holds itself without a Box. A function can have size parameters (`fn dot<n>(a: Array<Int, n>, ...)`): its type is `TForall`, `genericCall` instantiates them with new unknowns that the arguments decide and writes the sizes as the last arguments of the call (a constant, or a size parameter of the caller), the sizes are Int parameters of the function that the body and the contracts can read, and the validator asserts `size(a) = n` for a local of type `Array<T, n>` (`withTypeFacts`). A parameter written `&T` has the type `TRef T` in the function's type (`checkType` refuses it anywhere else) and `T` in the function: `checkFunction` strips it (`unref`), `tcReadOnly` forbids assigning it, a call checks the argument against `T` (`checkCall`, `genericCall`), and MirLower marks the parameter in `fnBorrowed`. A Box holds any type that has a size, and an array of no size (`Array<T, ?>`) only behind one: `size`, `first`, `last`, `get` and `set` look through a `Box` of an array (`checkBuiltinCall`), `Array::boxed(n, x)` becomes `NewBoxedArray`, and `coerce` writes the unsizing conversion (the builtin `Unsize`) into an argument, a constructor field, a returned value or an assigned variable where a `Box<Array<T, N>>` is given to a `Box<Array<T>>`. The functions of an impl for a struct with parameters are generic functions named `<Vec>::push`: a call on an instance (`v.push(x)` with `v: Vec<Int>`) looks the function up by the base name of the instance (`ownerOfValue`), and `callResolved` instantiates it with `genericCall` like any other generic function; a trait cannot be implemented for such a struct yet. `clone(x)` and `x.clone()` are the application of the builtin `CloneOf` (the MIR's `Clone`: the same value, which the validator and the executor take as a `Use`), and need the type to implement `Clone` (`implementsMarker`: Int, Byte, Bool and functions do, an array, list and Box have it when their elements do, a struct or enum when an `impl Clone for T { };` says so, whose fields `checkMarkerImpl` checks); `impl Copy for T { };` is checked the same way (and needs `Clone`) and gives back a `CopyDef T` statement for the lowering. A type parameter of a function is taken to be Clone, and a bound `T: Clone` or `T: Copy` is met by `implementsMarker` (`traitArguments`). `array(n, x)` and `Array::boxed(n, x)` need the type of `x` to be Clone, and a struct update `..clone(base)` is written by the parser as a `clone` of each field that is not given. A function with bounds on its types (`fn total<S: Sequence<Int>>`, a `BoundedDef`) is kept as a template and is not checked where it is written: each call decides the types, checks them against the bounds (`traitArguments`: a list, an array and a Box of an array implement `Sequence` and `Growable` as built-ins, a struct what its impls say) and makes the function for them (`total[Vec<Int>]`, checked by `checkFunction` like any other and put before the statement that made it), so the MIR never sees a bound.
3. `MirLower.lowerElaborated` lowers the checked program to the MIR of `Mir.hs` (see MIR.md): a `Program` of typed functions, each a map of basic blocks of simple statements ending in a terminator (`Goto`, `SwitchBool`, `Call`, `Return`, `Unreachable`). Lowering resolves the scopes to numbered locals, turns `if` into a switch whose branches meet at a join block (a condition made of `&&`, `||` and `!` is a switch for each of its tests, `lowerCondition`, and a Bool value made of them is the same tests ending in two blocks that assign `true` and `false`; a `while` records the first block of its body, `loopBody`, where the validator starts an iteration) (none when both return, and statements after a `return` are not lowered, so they are not validated either), `while` into a header block that the end of the body jumps back to, nested expressions into temporaries, a call into a `Call` terminator, builtins into `BinaryOp`/`ListOp`/`MakeData`/`ReadField`/`IsVariant` rvalues (`as` is `AsVariant`: the same value, typed as the variant), and lifts a function defined inside another to the top (`outer::inner`; a builtin used as a value becomes a small function of the program too). The AST has no types, so lowering replays the checker's inference (`TypeCheck`'s `TC`, the unifier that decides `x = []`'s element type from a later `push`) to give every local a type; a type no use decided is `Int`. The contracts, loop invariants, `shrinks` clauses and `affirm`/`define`/`rewrite`/`axiom`/`proof` statements are kept in the MIR as `Ghost` statements and a `FunctionSpec`, which the executor skips. Each is written with the names of the source, so it carries an `Env`, what each name stands for at that point (a local, or a function), and `GhostFunction` marks where a function is defined. `MirVerify.verifyProgram` checks that the result is well formed (every jump goes to a block, every local is declared and typed, and every operation is applied to operands of the types it takes) and lowering fails otherwise. A `Mark` becomes a `GhostPosition` statement (and is written again at the start of each block), `CopyDef T` (which the checker writes for `impl Copy for T`) is collected, and `MirMoves.checkMoves` then follows the places that are moved out (a local with the fields and elements followed from it) along every path of each function, with the views that a field, an element, a cast, a `Box::unbox`, a `match` and a `for` make of the place they read, and reports a use of a place after it was moved, a move out of a list or of a lent parameter, and a lent argument that is moved by the same call, with the line and the name (`Lowering failed: Move error: in f, line 9:5: ...`); `stripPositions` takes the places out of the MIR it gives back. `lib/lists.tersus` is lowered without the check (`lowerLibrary`).
4. `MirValidate.validateProgram` symbolically executes the control-flow graph of each function. A path through a function has a `PState` (`ProofState.hs`): the iota that each local holds (values never change, an assignment gives the local a new iota), the facts known (the standard library's and the functions' are kept apart, as they hold everywhere), the variables of proofs (`define`), the rules, and the solver of the facts (`FactCache`). A block's statements run in turn: `x = a + b` is a call of the builtin, which has to meet its input contract (`Ghost.applyCall`: `Div` needs a divisor proved non-zero, `Get` an index in range, and so on) and gives a fresh iota and the facts the builtin promises, tied to the operands (which are locals), so a contract like `push`'s `size(return) = size(list) + 1` or `set`'s `size(return) = size(list)` is usable. A user function's call is the same with the function's own contract, and nothing else: the callee's body is neither run nor read for facts (a builtin on known values is evaluated, since its definition is its contract). `affirm`, `define` and `rewrite` (`Ghost.runStatements`) read the names of the statement's `Env`, so they see the values the locals have there. A `SwitchBool` sends each way a state with the truth of the condition added, and the relation it compares when the condition is one, negated on the false edge. The paths that meet at a block are joined (`mergeStates`): a local that holds different iotas gets a fresh one equal to each, and a fact is kept if every path establishes it. The candidates are the first path's facts (checked in the others with the full engine) and, checked in all of them with `Engine.entailsDirect`, the proofs the program is about to need (`wantedAt`: the `affirm`s and loop invariants, with the variant check, in the blocks that follow, and the function's output contract about the value that a `Return` computes), the facts from before the join rewritten to the merged values, and the other paths' facts. A path whose facts contradict each other cannot run, so the join ignores it. A `Return` checks the output contract on its own path, and what the function exports is what its contracts say (`exportContract`: the contracts assumed in a state that knows nothing else, as facts about the parameters, the result and the names the contracts define), not what the paths establish; a function that can end without returning is `Return value not found`. A loop is a header block that a back edge returns to (`enterLoop`): it has to say how it ends (`loopTermination`), its invariant must hold on entry, the locals its blocks assign are given fresh iotas with no facts, and its blocks are walked with the invariant and the condition assumed; each path that goes back to the header must establish the invariant again, and the variant (when the loop has one) must have been at least 0 when the iteration started (`startIteration`) and be smaller at the end (`smallerThan`). The paths that leave the loop (the false edge of the header, a `return` in the body) go on from the state with the condition false. Loops also get inferred invariants (`inferInvariants`): candidates from the entry values of the locals the body assigns (`Engine.constantValues` gives the constants, and the constant size of a list that is not a literal), and comparisons with the variables the loop leaves alone that `Engine.entailsDirect` (congruence and arithmetic only, no forall) says already hold; the loop is walked with the survivors assumed and every candidate it does not preserve dropped at once (`houdini`); if the loop is refused with an error that names an inferred invariant, it is validated again without, so errors are about the program's own invariant. A function is validated where the program defines it (`GhostFunction`): its body against the facts that hold everywhere, with its input contract assumed and its output contract checked on every return. A function defined at the top can call itself, with its output contract assumed for the calls (`Recursing`), and a function that calls itself must say why it ends (`shrinks e`, or `~`): `startFunctionVariant` checks the variant at the start and keeps its value in `variant at entry`, and `callTermination` checks the variant of a recursive call's arguments against it. Whether code is guaranteed to terminate is not a fact of the state but an error at the source: a function that is not `~` is validated with `psTerminates`, and a loop or call that may not end (`noteDivergence`) is rejected then when the facts are not contradictory (`unreachable`). `axiom` and `proof` declarations register validation-only rewrite rules. A contract can call a function of the program (`f(x)` in a proof is `FApp (ATerm "f") [x]`, resolved by `inferProofR`): `Ghost.evaluateCalls` looks for the calls in a proof that is asserted or assumed, checks the arguments against the input contract of the function and adds the facts of its promise (`fnExported`) about the term `$f(x)`, once on a path (a marker fact `$evaluated`), and `exportFacts` keeps the function iotas of the program as constants. A struct with an invariant (`progInvariants`) has it checked by `checkInvariant` at each `MakeData` and each constant, and assumed as facts about any local of its type (`withTypeFacts`, `typeInvariants`) and in the contracts of a function (`exportContract` is given them).

5. The proof engine, `ProofEngine`, decides what the facts of a state entail. `affirm` asks it whether a proof is entailed (validation is a bounded search that is sound but incomplete: what it cannot prove is rejected as `Could not prove: P`, and the program adds `affirm`s, `define`s and `rewrite`s until it can, see LANGUAGE.md; `*`, `/` and `%` bind tighter than the other infix operators, and `/` and `%` must have a divisor proved non-zero; a failure reports the proof in source syntax, rendered by `Pretty.renderVarProof`) (a congruence closure over the known equalities, so equal arguments give equal results without any rewriting, plus difference constraints over its classes for integer comparisons, so `s = 3` gives `s > 0` and `i < n` gives `i + 1 <= n` (`x != y` facts and `c * x` terms are folded in by `refine` in `arithmeticEdges`, which adds edges the graph so far implies: `x <= y` with `x != y` is `x < y`, and `x - y <= d` is `c * x - c * y <= c * d`); the closure is built from use lists (`Closure`), and a `Solver` of the visible facts is kept in the state (`FactCache`): the places that add facts add them to it too, and a question uses it only when every fact it holds is still visible, adding the facts it lacks, so a long program does not intern every fact again at each `affirm`), and `rewrite` applies primitive or user-defined rules to expand that context (applying a rule only adds its outputs, with no `refl` copy of the other facts). A `forall` is a proof form `Forall index guards body` whose index is a `BVar`, interned as one term in the closure; `entailsAll` proves a `forall` goal for a fresh index meeting the guards, and instantiates `forall` facts at the `get(L, t)` terms it finds (`forallInstances`). `push` and `set` also export `return = push(list, x)` or `set(list, index, x)`, which the standard library rules `pushKeeps`, `setKeeps` use to say a given index is unchanged. A smaller `shrinks` value is the internal builtin `Within`, entailed when the engine finds the first term among the field reads of the second (`partOf`), and a comparison of differences `x - y` with zero or with each other is turned into one of their sides (`differenceEntails`), since the difference constraints say nothing about the difference as a term. What the graph cannot decide goes to `Linear` (`linearSystem` turns the facts into equations and inequalities between the classes: `t = a + b`, `t = c * a`, `c * t <= a <= c * t + c - 1` for `t = a / c`, `a = c * q + t` with `t` from `0` to `c - 1` for `t = a % c` (a divisor that is only known to be positive bounds `t` too), `size(l) >= 0`, and the relations; `linearEntails` asks whether they have a whole-number solution together with the negated goal): Gaussian elimination of the equations, rounding of each inequality's constant, then Fourier-Motzkin elimination (given up on past 300 constraints), only when some fact has an operation the graph cannot take. `inferInvariants` also proposes `a + b = n` for two loop variables and a variable the loop leaves alone.
6. `MirEval.runProgram` runs the MIR: it keeps the locals of the function in a map and the block it is in, runs the statements, then follows the terminator (a `Call` runs the callee and stores its result in the destination), and still reports `Division by zero`, `Get index out of range` and the like, which validation is meant to make unreachable. `Int` is 64 bits and arithmetic traps on overflow (`Integer overflow`). `renderProgram` prints the MIR.

7. `MirLists.lowerLists` makes a validated program ready for native code (`Pipeline.nativeProgram`, used by `llvm`, `build` and `owned`): a `List<T>` becomes the struct `StdList<T>` of `lib/lists.tersus` (embedded by `PreludeSource`, compiled and validated once as `Pipeline.listLibrary`) in every type, name and constant; `size`, `get`, `first` and `last` become a read of `len` and of the element of the array that the struct holds (the address of a `StdList` is that of its Box of an array, so `LlvmEmit` reads an element from either), `push` and `set` become a `Call` of `stdListPush` and `stdListSet` (a call ends a block, so the block is cut there), and a list constant or `MakeList` becomes `stdListNew` and a `stdListPush` for each element. The library is merged into the program (`completeInstances` declares the `StdList<...>` instances it mentions) and `MirMono`, `MirOwnership` and `LlvmEmit` see an ordinary struct that owns a Box of an array; the runtime prints and compares a struct named `StdList` as a list (`Variants.tagged` is 2). `Array::empty()` (`ListOp NewEmptyBoxed`) is the array of no elements, so an empty list needs no value of its element type.

The CLI in `app/Main.hs` drives these paths over a source file (logic in `src/Cli.hs`):

- `stack run -- check <file>` parses the program, lowers it to the MIR and validates that, printing `OK` on success.
- `stack run -- run <file>` validates the program, and only if that succeeds compiles it to native code (the lowering and LLVM path of `build`, so it needs `clang`), runs the executable and prints its return value (nothing is printed when the program does not `return`). The executable is removed afterwards and its exit status is the one of `run`.
- `stack run -- eval <file>` validates the program and runs its MIR with the reference interpreter (`MirEval`), which needs no compiler. It is what native code is tested against, and not the way a program is run.
- `stack run -- mir <file>` validates the program, and only if that succeeds prints its MIR.
- `stack run -- owned <file>` validates the program, and only if that succeeds prints the MIR that native code is made from, with the moves, copies and frees (`MirOwnership`).
- `stack run -- mir --data <file>` prints that MIR as data, in the line-oriented format of `MirData` that a program can read (what the emitter in Tersus of step 31 is given, see `STEP31.md` and MIR.md, The MIR as data); `examples/mir_reader.tersus` reads it from the standard input into the types of the MIR, written in Tersus, and writes it again (`tersus mir --data p.tersus | tersus run examples/mir_reader.tersus`), and `examples/emit.tersus` is the lowering to LLVM IR written in Tersus, which writes all of the IR of a program (`tersus mir --data p.tersus | tersus run examples/emit.tersus`; the arguments `outline` and `bodies` write the parts it was written in).
- `stack run -- llvm <file>` validates the program, and only if that succeeds prints its LLVM IR (`LlvmEmit`); `stack run -- build <file> -o <output>` compiles that and the C runtime (`LlvmRuntime`) with clang (`Native`). Native code handles every type of the language. The IR is written by the emitter in Tersus, `examples/emit.tersus` (step 31, `STEP31.md`), unless `--haskell-emitter` comes before the command (`stack run -- --haskell-emitter llvm <file>`), which has `LlvmEmit` write it and needs no clang to print it. The Tersus emitter is built with clang the first time it is used, in two stages (`Bootstrap`): the seed, the IR of an emitter that is kept in `bootstrap/emitter.ll`, is built (stage 0), and it compiles the emitter as it is now (stage 1). Both are kept in the cache directory of the user (`$XDG_CACHE_HOME/tersus`, or `~/.cache/tersus`), named by a hash of what they are made of, so the first `build`, `run` or `llvm` takes about a minute and a half and the next ones do not. The IR is the same text as `LlvmEmit` writes.
- Use `-` as the file to read the program from standard input.
- Errors go to standard error, prefixed with `Parse error:`, `Validation failed:`, `Lowering failed:` (a bug: a program that type checks always lowers) or `Evaluation failed:`. The exit code is 1 for a failed program and 2 for bad command-line usage.

14. Termination proofs written in the validation language (the clause today is `shrinks e` or `~`, see LANGUAGE.md, Termination)

15. `&&` and `||` in conditions
    Done: a condition (and a Bool value) can combine tests with `&&`, `||` and `!` (LANGUAGE.md, Connectives). They are short-circuit sugar for nested `if`s, lowered by `MirLower.lowerCondition` to a switch for each test that is evaluated, so the validator needs no new reasoning: the right test of `a && b` is checked knowing `a`, the body of a loop with `a && b` knows both, and `affirm a && b;` is two statements
    What is left is what a proof can say: a disjunction as a fact (split into cases) is a much larger change, so after an `||` the validator knows only what both tests give, and a proof has no `||` or `!`
16. Conditional contracts
    An output contract cannot say something that depends on which variant is returned, such as "if `parse` returns `Parsed::Message`, its payload fits in the buffer"; the property is true by construction today and cannot be stated to a caller
    The intended form is an implication in contracts, `affirm return is Parsed::Message => size((return as Parsed::Message).payload) <= size(buf);`, proved for each way out of the function and assumed by a caller once it knows the variant. A single implication to start with, not general `||` inside proofs
17. LLVM
    Validation walks the MIR (`MirValidate`), and the AST has no evaluator any more: the MIR executor runs programs. The MIR is lowered to LLVM IR (`LlvmEmit`, MIR.md, Native code) in steps, each checked against the executor by building and running programs:
    1. Done: `Int` and `Bool`, control flow, calls and recursion, the overflow traps, and the printing of the result
    2. Done: lists, with a runtime of C (`LlvmRuntime`): literals and operations, structural equality and printing by a descriptor of the type
    3. Done: structs, enums and function values: every example builds natively and prints what `tersus eval` prints
    4. Done: memory (`MirOwnership`, MIR.md, Ownership): every value of the heap has one owner, the last use of a local moves the value out of it, a value that is wanted twice is copied, values are freed when their owner lets go, and `push`/`set` change the list in place; a list built by pushing takes time and memory in proportion to its length
    5. Borrowing a value to a function that only reads it, so that a call does not copy an argument that is used afterwards
        Every parameter is owned today (MIR.md, Ownership), so `helper(l, i)` called again and again on a list that is used afterwards copies the list at each call, which makes a loop of such calls take time in proportion to the square of the length. The pass already decides move, copy or look per operand, so a borrowed argument is a fourth outcome, plus an inference of which parameters of a function it only reads (a fixpoint over the calls: a parameter is owned if some path moves it, or passes it where it is owned)
        What needs care: a function reached through a function value (its convention has to be one for every function, or a small wrapper made when a function is used as a value), a value passed both borrowed and owned in one call (the owned one has to be a copy), and the check of the result by the model of the heap (`TestOwnership`), which has to learn what a borrowed parameter may do
    6. Deep recursion and deep values
        Native recursion uses the C stack, and freeing or copying a very long recursive value (a million-node list built of an enum) recurses too, so either could overflow it, where `tersus eval` has no such limit. An iterative free and copy, and a bigger stack or a clear error when it runs out, would fix both
    7. Contracts as hints to LLVM
        The code assumes what validation proved (a divisor that is not 0, an index in range, a list that is not empty) without checking, but LLVM does not know the proofs, so it cannot drop the work around them. Emitting `llvm.assume` for the facts that justify each `get`, division, `first` and `last` could let it. A mistake in the validator would then be wrong code that the optimiser has built on, so it needs the memory and answer checks of the tests to run with the hints on
    8. Cheaper ownership
        A part that is kept (`row = get(rows, i)`) is copied, and so is the inner list of `rows = set(rows, i, push(get(rows, i), x))`, which costs the size of the inner list where a move out and back in would cost nothing; a field update through `..p` copies a list field unless `p` is dead; a value that is read for the last time is only freed when its local is assigned or the function returns; and only temporaries can look at a value, not named locals that are only read
    9. Run the valgrind checks in CI
        `testNative` runs some programs under valgrind when it is installed, and the CI runner does not have it, so there only the checks of the runtime (`-DTERSUS_CHECK`) and the model of the heap run. Installing it in the workflow would keep the independent check
21. Generics over traits (done in the form of a copy of the function per type; the modular form is planned, see 24)
    A function can take "any type that implements a trait": `fn total<S: Sequence<Int>>(s: &S) -> Int` (LANGUAGE.md, Bounded types). The bound is a `BoundedDef` that the parser writes and the checker keeps as a template (`tcTemplates`); each call decides the types by unification, checks each against its bounds (`traitArguments`: a list, an array and a Box of an array implement `Sequence`, a list also `Growable`, a struct what its impls say), and makes the function for them, `total[Vec<Int>]`, checked by `checkFunction` like any function and put before the statement that made it (`tcEmitted`). So the MIR, the validator, `MirMono` and native code have no bounds and no change, and a contract of the function is proved for each type. What is chosen for now: the body is checked for the type and not against the bounds alone (it may call any function the type has), a call of itself must give its own types (`tcActive`), and the types of a call cannot be made of a type parameter of the function that calls. The modular form (validate the body once against the trait's contracts, with a placeholder for the trait's functions on the type parameter and the call sites substituting them) is step 24.
    The functions that check an impl against its trait are the obligations a generic function relies on. What is still missing is that a trait cannot say that its functions end (an impl may be `~`), which a generic function that relies on termination would need
22. More of traits and impls
    Impls written for `Int`, `Bool` and lists (`impl Measure for List<Int>`; a list, an array and a Box of an array already implement `Sequence` and `Growable` as built-ins that `traitArguments` knows by name, which a program's own trait of the same name and one type would also get), default bodies in a trait (a default has to be validated for every `Self`, so it needs the generics of step 24), a trait that names other traits it needs (a trait can already call the functions of the traits declared before it on `Self`, as `Growable` does `size`), traits with sizes, associated constants and types, type parameters for an enum and for a function of a trait impl, and a bounded function in an impl or as a value. The functions that check an impl are compiled into the executable although nothing calls them; they could be left out of the MIR after validation
24. Generic validation of bounded functions, and the list facts on the traits
    Two steps that belong together. (a) A function with bounds is validated once, against the contracts of the traits, instead of for each type (step 21 copies it): a call of a trait's function on a type parameter (`size(s)` for `S: Sequence<Int>`) is a placeholder `<S as Sequence>::size(s)` whose promises are the trait's elaborated contracts; the call sites substitute the placeholder with the function of the type they give (`MirMono` already finds the types of a call), and the executor dispatches the placeholder on the value. That lets a function with a type parameter of its own call one with bounds, makes the body unable to use more than the bounds say, and lets a bounded function be in an impl or a value. (b) The proof engine's facts about lists (`size(push(l, x)) = size(l) + 1`, `get(set(l, i, x), i) = x`, the frame of `pop`) are the `forall` facts of the contracts of `Sequence` and `Growable`, instantiated for calls of the trait's functions, so the builtin overloads of the checker and the engine's list knowledge go and a list is a library type in the validator as it is in native code.  The MIR would need the bounds of a function (`fnBounds`) and which parameter of a trait function is `Self` (`progTraitFns`).
25. Raw pointers, with manual allocation and drop
    Today ownership is implicit: `MirOwnership.insertOwnership` decides every `Move`, `Clone` and `Drop` of a value that `needsDrop` (a list, a `Box`, and a struct, an enum or an array that holds one), and a program cannot say where a value is freed or point at one without owning it. A raw pointer type `*T` would be the escape hatch under it, so that `Box`, lists and user collections can be written in the language and not only built into the emitter: `alloc(n)` for room for `n` values of a type, reading and writing through a pointer (`*p`, `p.offset(i)`), and `free(p)`, all of which the program does by hand. The checker marks them (a function that uses one says so in its signature, as `~` says a function may not end), and the validator takes over what the borrow-like rules cannot: a pointer is valid between its `alloc` and its `free`, in range for the size it was made with, and freed once, which are contracts on the three builtins (`affirm valid(p)`, `affirm i < size(p)`) that the program proves, the way `get` asks for `i < size(l)` now. A value that holds a raw pointer does not `needsDrop` by itself: the ownership pass leaves it plain and the program is responsible, until step 26 gives it a drop. In the MIR it is a word like the address a `Box` holds (`arrayPtr`), with `Load`, `Store` and `PtrAdd` rvalues and the C runtime unchanged. The first user of it would be `lib/lists.tersus` and `examples/vec.tersus`, written on a pointer and a count and not on `Box<Array<T>>`
26. User defined drops
    `impl Drop for T { fn drop(self: &mut Self) ... }`, a trait that `MirOwnership` calls where it now emits a `Drop` of a struct, and the way a type that holds a raw pointer (step 25) frees it. What it takes: the ownership pass asks "does the type have a drop, or hold something that does" in `needsDrop` (a struct with a drop is never plain, whatever its fields are) and emits a call of the impl's function before the fields are dropped, in the order of the fields; `Drop` of a moved-from value is not emitted, which needs drop flags in the MIR for a value that is moved in one branch and not the other (today the ownership pass inserts a `Move` and a `Drop` per path and needs none); a copy of a type with a drop is its `Clone` or an error (`Clone` and `Copy` exist, and a type is not Copy unless it says so), since a bitwise copy would free twice; a drop may not fail or end late (it is a function that ends, which the termination checks already say, and its contract is that it frees what the value owns); and the validator needs the drop to be a call it sees, because what a program proves about a value must not depend on a free that happens at the end of a block. `Box<T>` and lists keep their drops in the runtime until the library versions of step 25 replace them
27. Linear types
    (Copies are explicit now: a value that is not Copy is moved, `clone(x)` is a copy, and `MirMoves` follows the places that are moved out along every path and reports a use of one, which is the half of this step that tells a value that was moved from one that was not. What is left is the rule that a linear value has to be moved on every path, the obligations of `DROPS.md`, Part 2.)
    A value that must be used exactly once: a `linear struct` (or a `linear` mark on a type) that cannot be dropped without being consumed, copied or ignored, and is passed on, returned or consumed by a function that takes it by value. It is the guarantee that a handle (a file, a lock, a pointer from step 25, an in-flight request, a value that has to be closed) is not forgotten, and the other half of step 26: a drop is the implicit use of a value at the end of its scope, and a linear value has none, so the checker reports a linear local that is still alive at a `Return` or at the end of a block (`x is linear and is not used`), and a use after the use (`x was moved`). The checker needs the flow the ownership pass has (which locals are live at each point of a block; `MirOwnership` has it for lists), so it is written over the MIR and its basic blocks and not over the statements, and a branch has to use the value on every path or on none, a loop body may not consume a value of the loop that it did not make, and a function that may not end (`~`) is allowed to leave one, since it never reaches the end. The validator gains a small fact: a linear value is used once, so what a contract says of it before the use cannot be said after, which the rename to a new value (`x2 = close(x)`) already gives. Affine (at most once) is the same check without the leftover rule and is the first step; `linear` adds the leftover rule, and a type with a drop is affine
28. Preparing for async / await
    Nothing in the language is asynchronous, and the design is not chosen. What is true of the MIR is that it suits it: a function is a map of basic blocks that end in a terminator, so a suspension point is a `Call` that may not return at once, and the frame (the locals, `fnBorrowed`, the slots `alloca`ed in the entry block) can be turned into a state that the function keeps while it waits, as Rust's generators are. The steps that prepare for it, none of which needs `async` in the syntax: (a) a trait `Future<T>` with a `poll` (or a `Task`/`Waker` pair) that an `impl` can give, so a runtime is a library; (b) lowering a function with suspension points to a state machine in the MIR (`MirCoroutine`, after validation and before ownership, like `MirLists`), with the locals alive across a suspension as fields of the state; (c) the rules that make that safe, which are exactly the ones of steps 25 to 27: a borrow (`&T`, which only a parameter has today) may not be held across a suspension unless the state owns what it borrows, a raw pointer in the state is the program's responsibility and a linear value in the state must be used when the future is dropped or cancelled (so a drop of a future is a cancellation, and runs the drops of the locals alive at its suspension point); (d) what the validator proves across a suspension: the facts of a local survive it, the facts about anything shared do not, and a contract of an `async` function is about the value it finally gives; and (e) the termination checks: a loop that awaits is not a loop that shrinks, so `shrinks` needs a reading for it (or `~`) and a call of `await` in a function that has to end is allowed only on a future that is known to. Strings, input and output (step 20) give a program something to wait for, so they come first, and the order of this block is 25 (pointers), 26 (drops), 27 (linear types), then 28 on top of them
29. `Box` defined in Tersus, and no special cases left in the compiler
    After steps 25 and 26 a `Box<T>` is a raw pointer that owns room for one `T` and frees it in its drop, so it can be a library struct (`struct Box<T> { ptr: *T }` with `impl Drop`, `new`, `unbox`, and the deref the language gives every smart pointer) the way `StdList<T>` is already. What the compiler does for `Box` by name today, which has to become the library's or a general rule: `TBox` in `Type` and `MakeBox` and `Unbox` in the MIR; reads of a field, `match` and the builtins of arrays through a Box "transparently" (the checker looks through it, `Box::unbox`), which becomes a deref rule that any type with a `Deref` impl gets; the check that a recursive type has a `Box` in its recursion (`checkFinite`), which becomes "a recursive type goes through a type of known size, such as a pointer" and is asked of `*T` and not of a name; the fat `Box<Array<T, ?>>` (two words, kind 7 in the runtime, `Unsize`, `NewBoxed`, `Array::boxed`, `Array::empty`), which becomes a pointer with a length (`*[T]`) and its coercion from `*[T; N]`; and the runtime's clone, free, compare and print of a Box by descriptor, which become the impl's `Clone` and `Drop` and the derived equality and printing of a struct. The same pass over the rest of the list of things the compiler knows by name: `List<T>` as a builtin type (`TList`, `ListOp`, the overloads of `size`, `get`, `set`, `push`, `first`, `last` and `pop` in `StdLib`, and the proof engine's list facts: steps 7(c) and 24; `MirLists` and `Variants.tagged == 2` for printing a `StdList` stop being needed when `List` is a library struct of the prelude); `Array<T, N>` (`TArrayOf`, `NewArray`, `ArrayFrom` and the `#[...]` literal), which stays a builtin of the language as the inline array and is the one type the library cannot make; the traits that `traitArguments` gives lists, arrays and Boxes by name (`Sequence`, `Growable`), which become impls in the prelude; the methods of `listMethod` and `sequenceFunction`, which become the general call of an impl's function; the reserved names (`StdList`, `stdList...`) that stop a program from using the library's; and the builtin names that a program cannot define (`size`, `first`, ... and `pop`). The test of being done is that the compiler's source mentions no library type by name (`Box`, `List`, `StdList`, `Vec`) except where a language item is declared (`#[lang = "box"]`, for the allocator, deref and the unsizing coercion that no library can write), and that `lib/` and `examples/vec.tersus` are the only places those types are defined. The order is: pointers and drops (25, 26), the proof facts on the traits (24), `List` as a prelude struct (the case where nothing is lost: it already is one natively), then `Box`, and last the language items that are left
30. Less C: the runtime written in Tersus
    `LlvmRuntime` is about 500 lines of C that the emitted IR calls, and everything in it is either something Tersus will be able to say once steps 20 and 25 to 29 are done, or one of a few things only the operating system can do. The pieces, with what replaces each: (a) `tersus_drop`, `tersus_clone`, `tersus_equal` and `tersus_print`, which walk a `Type` descriptor at run time, become code made per type: `MirOwnership` and a derive step emit a `Drop`, `Clone`, `Eq` and `Display` impl for each struct, enum and array in the program (the same monomorphization `MirMono` does for generics), and the descriptor tables (`Type`, `Variants`, `ArrayInfo`, `KIND_*`) and the `tagged == 2` case for `StdList` disappear; (b) `tersus_box_new` and `tersus_box_free`, `allocate`, `release` and `reallocate` become the library `Box` and list of steps 25 and 29, on a raw pointer, over two or three built-ins for memory (`alloc`, `realloc` and `free`, which the emitter turns into calls of the system's allocator, or `mmap` and `munmap` if the program is to link nothing); (c) `TERSUS_CHECK`, the checking allocator that the tests build with (live-block count, `0xDD` fill, double-free and leak reports), becomes a debug allocator in Tersus that a program or a test selects, and valgrind stays as the second opinion; (d) `fail`, `tersus_overflow` and the exit status become `exit(code)` and `write(fd, ptr, n)` as the only two system calls the language knows by name (`writeByte` and `readByte` of step 20 are the first of them, one byte on the standard output and one from the standard input), and the message is a string constant of step 20; (e) `main` and the printing of the return value become a library function (`fn main_result<T: Display>(x: T)`) that the emitter calls from `@main`. What stays outside Tersus at the end is the part that talks to the system: the entry point and the symbols `alloc`, `realloc`, `free`, `exit` and `write` (an `extern fn` declaration that the emitter turns into an LLVM `declare`, linked against libc, or inline assembly for a freestanding build), and the LLVM IR itself. The order is: the derived impls (a), which need only step 26 and not strings; then the allocator and the library `Box` (b, c), which need 25 and 29; then (d) and (e) with step 20; and the test that it is done is that `LlvmRuntime.hs` holds only the declarations of the system functions and `tersus build` needs no C compiler for the runtime, only for the link. `TestNative` and the heap model of `TestOwnership` are the oracle throughout: each piece is moved over while the old C is still there to compare with.
31. The lowering from the MIR to LLVM IR written in Tersus
    The plan, with measurements and the slices, is in `STEP31.md`; this is the description it started from.
    `LlvmEmit` (1250 lines of Haskell) turns the owned MIR into the text of a `.ll` file, and it is the part of the compiler that is closest to being a plain program over a data structure: a tree in, text out. Writing it in Tersus is the first step of the compiler writing itself, and it is a good test of the language because it is large, has no I/O except reading the MIR and writing the IR, and has an oracle (the Haskell emitter) to differ against. What it needs from the language, so what has to be done first: strings and a growable text buffer, and input and output of text (step 20); enums with data for the MIR (`Program`, `Function`, `BasicBlock`, `Statement`, `Rvalue`, `Type` are all enums and structs, which the language has) and `match` over them, which it has; a map from names and locals to numbers and to types (an ordered map or a hash map as a library over `List` and the traits of steps 22 and 24; today only lists and arrays exist); lists of lists and of structs that own lists (done); recursion over trees (done, with `Box`); and a validator that is fast enough to prove a program of this size, since every function of it goes through `MirValidate` (the symbolic executor is the part likely to need work first, as the proof engine is quadratic in the facts of a path). The MIR has to reach the program as data: either `tersus mir --data` prints it in a stable text form (an S-expression, or the `Pretty` form made parseable) that the Tersus emitter reads, or the Haskell side is kept for the front end and hands the MIR over as a value of the same types, which is the later form once the front end is also in Tersus. The steps: (a) fix the serialization of the MIR and a reader and writer of it on both sides, with a test that `read . print = id` for every example (done: `MirData`, `tersus mir --data`, `TestMirData` for the Haskell side, and `examples/mir_reader.tersus`, the types of the MIR and a reader and writer in Tersus that read the data of every example, itself included, and write it again, `TestMirReader`; (b) is begun: `examples/emit.tersus` has the declarations, the descriptors of the types and the entry point, which `TestMirEmit` compares with `LlvmEmit.emitOutline`, and the code of the functions that make words (operands, arithmetic with its overflow checks, the terminators and calls), compared with `LlvmEmit.emitBody`; now all of the IR, byte for byte the same as `LlvmEmit.emitOwned` for every example and native-test program, `TestMirEmit`; and the wire-in and the bootstrap of (c) and (d), `Bootstrap`, `TestBootstrap`: done); 18. Validate calls of function values
    The validator does not follow a call of a function that is a value: `fn apply(g: fn(Int) -> Int, n: Int) -> Int { return g(g(n)); }` is refused with `Function object not validated`, though the type checker, the executor and native code run it. The tests of native code for function values lower the programs without validating them (`functionPrograms` in `TestNative`) because of this
    The function a call reaches is not known statically, so the call needs the contract of the function type (the contracts of a parameter that is a function would be written in its type), or the callee has to be one of a known few
20. Strings, and input and output
    Done: strings (LANGUAGE.md, Strings; a literal can be written in a proof, and `concat` promises its bytes), output (Output, with `writeError` for the standard error), input from the standard input (Input), the command-line arguments (Arguments) and files (Files). A literal is a `String` of UTF-8 bytes, a library struct over a `List<Byte>` (`lib/string.tersus`) that implements `Sequence<Byte>` and `Growable<Byte>` and has `concat`, the readers and writers, so native code and the validator needed nothing new for strings. Everything that touches the world is a few primitives that are `ListOp`s of the MIR: `writeByte` and `writeError`, `readByte`, `argCount` and `argByte`, and `pathByte`, `fileLoad`, `fileByte`, `storeByte` and `fileStore` (a path is built a byte at a time and a whole file is loaded or stored), with the C runtime calling `putchar`, `getchar`, `argv` and `fopen`, and the interpreter threading the input, the path and the files through its monad (`MirEval.runProgramEnv`: `RunEnv` is what it is run in, `Outcome` what it did, including the files written, which the CLI writes when the program has ended). The validator knows only the range of what the reading ones give (`Mir.readersOfInput`, `FnInfo.fnReads`: a function that reads is not a function of its arguments, and a proof may not call one). The type `Byte` (LANGUAGE.md, Bytes: `TByte`, `toByte(x)` and `toInt(b)`, the range of every `Byte` known to the validator) is what a string is made of, and a number written out is a `Byte` where one is wanted (`TypeCheck.coerce`). What is left of the step, each a design of its own: what the later bytes of a `concat` are without naming the element (the engine does not match `size(a) + j` with a constant index, and a `forall` over a range that is not `0..n` was not preserved by `push`), printing a returned `String` as text, appending to a file, streams and directories, the environment, `write(fd, ptr, n)` and `read` as the only system calls (step 30), and what the validator says of an effect (today it says nothing: a program that fails does not take back what it wrote, the proofs cannot mention what was written or read, and two reads are two unrelated values)
23. Sizes, `Box`, and the data model without implicit heap values (the plan for arrays; DATA_MODEL.md, Sizes and Box)
    `Array<T, N>` (LANGUAGE.md, Arrays) is held inline with a constant size, and holds any value that has a size. The design agreed for the rest: a type has *size parameters* (`Array<T, n>`, and a user type may declare one, `struct Packet<T, n: Int> { ... }`), each a constant, a variable of generic code, or `?` (which may be left out: `Array<T>` is `Array<T, ?>`). A type with a `?` is unsized and is only used behind a pointer, and a pointer to a type carries the values of its `?` parameters in hidden words: `Box<Array<T>>` is a pointer and a length, `Box<Array<T, 3>>` a thin pointer. `Box<T>` is the owning handle (heap ownership is not in `Array`), `&T` a borrowed one later. A pointer to `S<c>` converts to a pointer to `S<?>` by storing the constant in the hidden word. A struct or an enum is an ordinary inline value of the words of its fields (an enum a tag and its largest variant), copied by value, and a recursive type holds its recursion in a `Box`; a list stays the one implicitly heap-allocated type until it is rebuilt as a struct of a `Box<Array<T>>` and a count. The steps, in order:
    1. Size arguments in types, with `?` and its omission (done: `TArrayOf element Size`; an unsized array is refused as a value, and is used behind a `Box`)
    2. Words per type: structs, enums and arrays inline wherever they are made and as fields and list elements, and ownership that asks "does it need to be dropped" and not "is it on the heap" (done: `slotsOf` gives the words of a type; a struct is its fields' words and an enum a tag word and the widest variant, held in the frame, in a field or in a list and copied by value; `needsDrop` says which values own a list or a `Box`, which are then moved, copied and dropped like a list was, with the words cleared when moved from; the runtime walks every value by its descriptor and the words in place)
    3. Thin `Box<T>` with explicit allocation (`Box::new`), transparent to field reads, `match` and the builtins on arrays, and the check that a recursive type has a `Box` in its recursion (done for structs and enums: `TBox`, `Box::new`, `Box::unbox`, `MakeBox` and `Unbox` in the MIR, `checkFinite`; a Box is transparent in values, and natively it is a pointer to room on the heap for the words of what it holds; a Box of any other sized type and the builtins on a Box of an array came with step 4)
    4. Unsized types: `?` behind a pointer, the hidden words, `Array::boxed(n, x)` for a size known only when the program runs, and the unsizing conversion (done: `Box<T>` holds any type that has a size; `Box<Array<T, ?>>` is a fat pointer of two words, the address and the length, held in line like a struct and freed and cloned by the runtime as kind 7; `Array::boxed`, the `Unsize` rvalue that the checker writes where a `Box<Array<T, N>>` is given to a `Box<Array<T>>`, and `size`, `get`, `first`, `last` and `set` looking through a Box of an array)
    5. Size parameters for functions and user types: `fn dot<n>(a: Array<Int, n>, b: Array<Int, n>)` validated once with a symbolic `n` and compiled once per constant, and `struct Packet<T, n: Int>` that is fat behind a `Box` for free (a size parameter may be `?` only in the last field, so the offsets before it are constants). Done for functions (`Size` has `SizeParam`, the checker's own unknown `SizeVar`, and a function with sizes has the type `TForall`; a call instantiates the sizes by unification and writes them as its last arguments; `fnSizeParams` marks them in the MIR; `MirMono` makes a copy per list of constants for native code); user types: a struct with sizes (`struct Packet<n>`) is a struct of its own for each list of sizes, named by them (`instanceName`, `instanceOf`; the checker declares one the first time it is looked at, `TcState.tcGenerics` has the declarations, `Mir.completeInstances` declares those the program mentions, and `MirMono` renames them with the sizes put in); enums, impls, `?` and type parameters wait
    6. Borrowed `&T`, for parameters only, so a read-only function costs no copy (done: `TRef`, which only a parameter of a function has, is its type in the function and cannot be assigned there; `fnBorrowed` marks the parameters in the MIR, `MirOwnership` lends them without a move or a clone and clones what the function takes of one, and native code reads the caller's words where they are)
    7. `List<T>` rebuilt on `Box<Array<T>>`, with `first`, `last`, `get` and `set` as functions of a trait that arrays and lists implement instead of the overload of the checker. In order: (a) arrays of any element type (done: `arrayElement`; an element that owns something is cloned into each slot by `array(n, x)`, dropped when `set` replaces it, and moved, cloned and freed with the array; a literal `#[...]` is still Int, Bool and arrays of them), (b) type parameters for functions and structs, monomorphized like the sizes (done for functions and structs: `TParam`, a capital name between the `<>` of a `fn`, `TForall` with the sizes and the types, `Signature` and `Function.fnTypeParams`; the checker instantiates them with new unknowns that the arguments decide, and `MirMono` makes a copy for each list of types by matching the types of the parameters with those of the arguments and of the result; a struct with types and sizes is a struct of its own for each list of them, named by them (`Arg`, `instanceName`, `instanceOf`, `typeText`), so `Vec<List<Int>, 3>` is declared like `Packet<4>` and renamed by `MirMono` in each copy), (c) the rebuilt list and the trait (done: `Vec<T>` and the traits `Sequence<E>` and `Growable<E>` as a library, see LANGUAGE.md, and one function over any of them with a bound, step 21; and the list of native code is a library struct: `lib/lists.tersus` defines `StdList<T>` (a `Box<Array<T>>` and a count, with an invariant) and `stdListNew`/`stdListPush`/`stdListSet`, validated on its own with the contracts of a list (`get` gives what `set` put, `push` adds one and keeps the others), and `MirLists.lowerLists` puts it in the place of every `List<T>` of a validated program before ownership, monomorphization and the emitter, which no longer have lists (the C runtime has no list, only a struct named `StdList` that it prints and compares as one). What it took: `functions in contracts`, `struct invariants`, `traits with types`, `impl<T>`, the prelude (which keeps the traits `Sequence` and `Growable`; `Vec` is the example `examples/vec.tersus`, and a list has its methods and `pop`), `Array::empty()` (an array of no elements, so an empty list needs no element) and reading an element out of a `StdList` where it is, so the part-that-is-only-read optimization is kept. What is not changed: the checker, the validator, the proof engine and the executor still know the builtin `List<T>` (its facts and its `size`, `get`, `set`, `push`, `first` and `last` as overloads), so the proofs about lists are as they were; moving them to the `Sequence` trait means giving the trait the `forall` facts of lists and making the proof engine instantiate them for calls of the trait's functions, which is the part that remains)
