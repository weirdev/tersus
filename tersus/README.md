## Tests

`stack test --test-arguments='-j 4'` runs up to four group processes, each
with one Haskell capability. Native, MIR emitter, MIR verifier and self-hosted
validator tests are each split into four batches. Original names such as
`testNative` select all four; `testNative:2/4` selects just that batch.
`--shard k/n` intersects these selections with the full-suite shard assignment.
All original leaf actions and prefix labels are retained. Native memory-limit
cases stay together because they execute one shared file. Self-hosted query
families share `TestHarness.compileOnce`, which validates the full validator
source and caches its lossless program across processes. Their four batches
stay on one shard to avoid repeating that cold compilation on every runner;
other batches remain individually shardable. The bootstrap test still runs as
a single group with its own cold cache.

Package test compilations use a lossless generic binary cache, retaining every
contract, proof, ghost, invariant and generic field. Keys include the selected
package sources, resolution probes, roots and unit policy, compiler/harness/codec source and version, actual selected
Haskell package identities, parser backend and runtime seed inputs. Unknown build
options conservatively add the compiled executable's SHA256; cross-rebuild
source-only reuse requires an explicitly approved build manifest. Interpreted
GHC/runghc execution bypasses this cache. Malformed, truncated, miskeyed or trailing
input is rejected, never tried with a legacy decoder. Only successful results are
retained; failures can be retried. See `dev/cache-codec/README.md` for measurements,
identity policy and scoped checks. Test executables use the native cache's existing
cross-process build lock. Group workers take the next heaviest group from one
bounded queue; results are still printed in registration order.

CI uses a 16 MiB GHC nursery. `dev/ci_resources.py` records the runner's CPU
and memory limits; `/usr/bin/time` records the unchanged test command's resource
use. `TERSUS_TEST_RTS_STATS=1` adds GHC allocation/GC statistics only to group
workers, not to command-line or probe processes they launch. These diagnostics
do not select or skip any test groups.

An eighth CI runner (`host`) runs `testHostValidation`, which validates the
compiler's own programs in full, one group per program, and fails on any
function that no longer validates. The verdicts are kept per function under
the validator's build in `~/.cache/tersus`, which the runner restores and
saves, so a pull request proves again only the functions whose data it
changed (the programs are still compiled on every run); the runner drops the
verdicts of older validators before saving, and on master it proves every
function itself rather than trusting restored verdicts.

## Validator written in Tersus

`lib/validation/validation.tersus` starts a Tersus implementation of validation alongside the
Haskell implementation, which remains the bootstrap and reference. Its first
query, `hasEquality`, treats integers as symbolic value identifiers and proves
reflexive, symmetric and transitive consequences of the supplied equalities.
`hasCongruence` additionally closes equalities over binary applications of
uninterpreted operators, including nested applications. The host must give each
term a unique identifier and distinguish different operators.
`hasApplicationEquality` accepts applications of any arity and treats the
function as a term, so equal functions applied to equal arguments are equal.
`hasApplicationOrder` uses those equalities while following comparisons. A false answer
means only that the query did not find a proof. General proof terms and MIR
validation remain incomplete, and the production pipeline still uses Haskell.

`hasStrictOrder` follows strict comparisons transitively and substitutes
equivalent identifiers at either end of a comparison. `hasOrder` also handles
chains mixing strict and non-strict comparisons. Neither query handles
general arithmetic expressions. `hasDifference` follows difference constraints
with checked 64-bit intermediate bounds, giving up on a path if a bound would
overflow; it does not detect negative cycles. `entailsApplicationOrder` detects contradictions
formed by a cycle containing a strict comparison and treats those premises as
inconsistent. `entailsApplicationDisequality` transports explicit disequalities
through equality, uses strict comparisons, and detects an equality contradicting
a disequality. `entailsRefinedOrder` also strengthens a non-strict bound to a
strict one when its endpoints are known to differ. Other forms of contradiction
are not yet covered.

`entailsGoal` combines these facts in a proof context. The context also
carries variant and constructor facts: values built with different variants
of one enum are different, equal constructor values have equal fields, a
field read of a constructor value is its corresponding argument, and a
`Within` goal asks whether a term is reached by field reads from another.
Scaling by a known factor, and division and remainder by a proved divisor,
give order facts around zero.
A size is known to be at least 0, so a loop bound
like `i <= size(xs)` holds on entry when `i` starts at 0.
The Tersus search is incomplete, so a negative answer does not establish that
the goal is false.

`validateExecution` tracks local bindings and sweeps each function's blocks
once, in an order where a block follows every block that can deliver to it.
The states that arrive at a block are merged before it runs, so a branch costs
its arms and not the paths through them. A merge keeps the facts both states
hold, gives a local bound to different terms a fresh one, and keeps the weaker
of the two sides' constant bounds and offsets for that term without asking the
search anything. A return block and a latch (a jump back to the loop header)
run once per arriving state and deliver nothing onward, and an empty block that
only jumps on forwards each arriving state unchanged. A loop is left with the
header's state under the failed test and with each state its body delivers to
the loop's exit (the false edge of a later `&&` conjunct of the test); these
reach the enclosing sweep only from a round in which every inferred invariant
held. One region round with N blocks run once, whose nested loops delivered B
states to their own exits, has at most 2N + 1 + B arrivals at blocks other than
forwarders and 2N + B merges, linear in the blocks of the nest for one round;
loop rounds still multiply with the nesting depth, and forwarding moves may be
quadratic in chain depth.
`SelfHostedMir.validateMirSubset` translates a subset of
typed MIR (copies, boxing, plain structs, pure binary operations, list and
array literals, empty and repeated-element arrays, length, indexed reads and updates,
first, last and list removal with known length, list append, assertions, jumps
and branches) to that representation. Reads require proof of their bounds, and literal sequence
elements have their known values. Append records the new length and element and
preserves previously checked reads; removal preserves known reads within the
shortened length. Simple relational invariants on non-generic structs are
checked at construction and assumed for typed values; enums are not yet
supported. It also checks a loop by its declared invariant over the loop region:
the header and every block that can get back to it are walked once, each edge
back to the header re-establishes the invariant and shrinks the variant, and a
block that leaves the loop is walked as an exit. A body with several blocks, a
return inside the loop, and a nested loop are handled the same way. Invariants are the declared
ones, with the facts the header itself establishes (the values' types and the
loop condition), and the relations the entry state proves in the families the
reference inferred (constant bounds, known starts and differences, comparisons
with what the loop leaves alone, and offset sums such as one between a counter
and the size of a list it pushes to), each kept only where the loop preserves
it (`inferLoopCandidateGoals`). A construct it cannot translate makes the whole program
unmodelled, and validation refuses it (Interpreter flow, step 4). Functions
are checked with symbolic parameters and simple relational input and output
contracts. Direct calls to previously defined functions check those contracts;
a callee whose output contract mentions a parameter it reassigns is not
modelled. This validator is the only one: every compilation validates through
it, and there is no other validator to fall back to.
What one arm knows and the other does not is lost where they merge, so two
sequential `if`s are not correlated: write the work that depends on the first
test inside it. A relation between two locals that each arm sets to constants
is lost too: after `if c > 0 { x = 1; z = 2; } else { x = 3; z = 4; }` the merge
keeps `1 <= x <= 3` and `2 <= z <= 4`, so in a block that runs once on the merge
(`affirm x < z; if y > 5 { return 1; };`) the affirm is refused, even with the
same affirm at the end of each arm; directly before a `return` it is checked
once per arm and holds. An affirm at an arm's end brings a fact back only where
the merge keeps its form or compares one of its ends.
Branch facts include both the boolean result and, for a saved comparison, the
relation between its operands at the time it was evaluated. A check of a boolean
term against a literal is discharged from the comparison that produced the term,
so `below = true` follows from `below` being `x < 6` with `x < 6` known. A
disequality asks for the opposite value, so `below != false` is the same claim
and `below != true` is its negation.
The symbolic executor records multiplication by zero or one, division by one,
and concrete products, quotients and remainders when they fit in a signed
64-bit integer. It also records the order of a scaled, divided or remainder
result around zero when the factor or divisor is known or proved.

`MirEval.runNamedFunction` lets the host invoke a lowered Tersus function with
explicit MIR values. It executes code without checking its input contract or
the types and invariants of host-supplied values; the host must establish these
before calling it. The regression tests check the functions of
`lib/validation/validation.tersus` directly (equalities, differences, safe products and
execution over hand-built blocks) and validate programs through it.

The native parser and AST reader import the shared token/type codec and AST
arena writer from `lib/data`. Their package entries are
`lib/parser/parser.tersus` and `lib/ast_reader/ast_reader.tersus`.
`PreludeSource` embeds complete tool package snapshots; the parser snapshot
includes a generated Unicode root-module file. The ordinary Haskell module
loader/compiler builds those tools without invoking the native parser itself.
Native tool fingerprints cover the snapshot paths and source contents.

The MIR emitter, checker and eraser import `lib/mir/support/support.tersus`
for phase-neutral type/declaration metadata and rendering. The codec still
owns Type/Size and the reader owns the MIR records. Each tool retains its
full layout rules. The eraser writes its output with the shared MIR writer
(`printProgramAsRead`, see MIR.md).

The emitter is one six-file `mir::emit` module: `types.tersus` owns its model,
layouts, names and context; `values.tersus` owns generation state and operands;
`operations.tersus` lowers rvalues and statements; `functions.tersus` emits calls,
control flow and function frames; `helpers.tersus` generates drop/clone/print
functions. `emit.tersus` assembles the output and is the only executable file.
Files import the declarations they use explicitly. Keeping one build unit retains
bare emitter identities and the single module-local foreign `String.then` method.
`PreludeSource.mirPackageFiles` embeds all six files; cache keys include their paths
and contents. The CLI entry, MIR protocol and runtime ABI are unchanged.

## Ownership host

`lib/mir/ownership/` implements ownership and reference-write expansion
in Tersus. `MirHousekeeping.insertOwnership` first runs the Haskell `MirMono`
adapter; the transformation itself is Tersus. The operand-role helpers the move
checker uses are in `MirMoves`, and the heap model of `TestOwnership` has its own
`needsDrop` classification. No Haskell ownership transform remains.

The native order is:

```
validate -> eraseGhosts -> expandRefWrites -> lowerLists
         -> insertOwnership (monomorphize, then Tersus ownership)
         -> verifyProgram -> emitter
```

The tool reads `pass expand` or `pass ownership` on its first input line,
then MIR version 2, and writes MIR version 2. Runtime headers, structural
`Type`/`Size` arguments, source names and every function are retained, including
implicit Drop/Clone implementations. `MirOwnershipData` preserves generic
struct templates, invariants, specifications and full ghost payloads outside
the runtime data. Numbered ghosts follow rewrites and block splits; missing,
duplicate, unrecognized or cross-function IDs are errors. Before `pass
ownership` changes anything it refuses a function with a negative block id, no
block 0, or a jump to a block that is not there. This transport does
not use `forNative` as its pipeline result.

The emitter executable also dispatches `pass ownership` and `pass expand`.
Its pinned stage-0 seed expands and owns every program the host builds for
itself (the emitter, checker, eraser, parser and validator), so those prepared
inputs are made concurrently; stage 0 emits the emitter to build stage 1, and
stage 1 emits the other tools and owns and emits user programs. Ownership runs
natively throughout that sequence. Only the recursive erasure of the List/Box
library uses the interpreted eraser while the native tools are being built. The host
names the compiler explicitly during builds to avoid re-entering owned-program
CAFs or cache locks. Build, execution, protocol and metadata failures return
`Error`; there is no Haskell ownership pass to call.

## Interpreter flow

The native parser produces the AST; the elaborator written in Tersus checks its types, Haskell lowers it to MIR, then the native Tersus validator checks it before execution (the stages are chained by `Pipeline`, which type checks the program once; steps 1 to 6 below):

The elaborator lends a stable resolved place directly to its `Clone` impl instead of materializing a copy first. A terminal Box field is lent as its owning handle; a stable `clone(Box::unbox(place))` with a non-array payload and lent Clone implementation borrows the payload through `&*place`, so recursive derived Clone visits each child once without consuming the source Box. Sized boxed arrays keep the whole-array materialization path; their terminal Box handles can still be lent. `MirLists` lowers that typed payload borrow to the existing slot-zero address step. `MirLower` retains the variant proof when that place includes an enum cast; the existing loan and ownership checks still govern the call. Index expressions containing calls retain the original materialization path, so later calls cannot change an earlier container snapshot.
For a file inside a package (`package.tersus`, see LANGUAGE.md, Modules), the compiler captures a snapshot of what loading the package reads (`Modules.captureFilesystemInput`) and sends it to the elaborator written in Tersus in one load request (`ElaborateRequest`, `PackageCompile.compileModulesUsing`; `lib/elaborate/load.tersus`); the CLI compiles a package from that one load. The elaborator discovers the package and its module graph (the entry module and the modules it imports, dependencies first, an import cycle between modules refused), parses each file in process with the parser's library (`lib/parser/syntax/`) in its module's declaration context with the constructors its actual imports supply (including the implicit library declarations, so a string literal parses in a module file), and elaborates each module in turn: it rewrites its references to canonical names (`lib/elaborate/resolve.tersus` and `rewrite.tersus`; the entry module keeps its bare names, another module's declaration becomes `package$module$file$Local`), gives it the implicit libraries its own files' text calls for (`lib/elaborate/libraries.tersus`: the rule a single file is read with, over the union of its files, plus the library types its direct dependencies expose: modules of the synthetic `tersuslib` package in `LibPackage`) and checks it against the interfaces of the modules it imports, with a separate checked defining dependency closure for imported templates (`Interface`); the compiler lowers it with the same private helper signatures, types and invariants (`MirLower.lowerModuleWith`) and merges the lowered units (`Link.linkPrograms`: the same library unit selected by several modules is kept once, deduplicated by unit identity, as is an identical `extern fn`, and a conflicting name — a user/library collision included — is a link error). The complete linked program is validated before ghost erasure or reachability pruning (`pruneProgram`), then follows the same ownership, list lowering and execution as a single-file program below. Package loading resolves configured external roots or sibling packages through the same module graph. It snapshots reachable modules, their markers, and root declarations consulted for import disambiguation; unrelated sibling contents and unimported module bodies are not read. Files share only their own module's declaration context and the constructors supplied by their actual imports, on both filesystem and in-memory routes. Root ambiguity probes read declaration names without following imports from an otherwise unused root module; exact relevant probe contents participate in cache identity.

The CLI accepts `--package-root name=directory`, `--std-root directory` (the ordinary package name `std`) and `--no-prelude` before the command. The loader refuses the package name `tersuslib` (`reservedPackage` in `lib/elaborate/load.tersus`), which is the compiler libraries' (`LibPackage`), for an entry package's directory, an import and a `--package-root` mapping, since the elaborator gives some modules of that package what no program's modules get. `Modules.LoadOptions` carries these inputs for API callers, including `Pipeline.loadFromSource` for source text. An empty package marker keeps current defaults; `noPrelude = true;` opts its entire package out, including installed dependencies inside a default user build. The entry-unit CLI option does not propagate to dependencies. A no-prelude program does not force implicit `LibPackage` data; a package load is given the compiled libraries, since which of its modules opt out is known only once it is loaded, and a failure of the libraries refuses only the first module that is given them. Native parser and validator tools retain their own bootstrap dependencies, and validation is unchanged. Existing selective implicit imports remain the default; installed std inputs do not activate a new prelude or relocate library sources.

A standalone file or stdin source can import only explicitly configured external roots; its working directory and neighboring package markers do not supply implicit providers. A file inside a real package retains ordinary sibling imports. Without root inputs standalone sources retain the existing source-only path. Each selected package's root, marker, effective policy, imports and exact source contents enter the existing test-program cache identity. Filesystem entry aliases resolve to their physical paths, and every used package root is compared at its canonical location. Ordinary relative source paths are retained for embedded-tool callers; explicitly configured filesystem builds use absolute paths.


The implicit compiler libraries are read and elaborated once per process as the
synthetic `tersuslib` package by one `libraries` load (`LibPackage`), one module
per lib file, and linked under bare names ahead of the entry module. Each
program is checked against the interfaces of the libraries the elaborator
selects for it (by the rule of `lib/elaborate/libraries.tersus`), so library
code is not re-elaborated per program; only the selected units are linked. The
libraries' sources travel with every load, and the elaborator parses them for
the declarations a program or module is read with.

The compiled validator's verdict on a function is kept for the rest of the
process under the data the bridge makes of that function (`ValidatorNative`):
that data holds the function's own blocks and contracts and the contracts of
what it calls, the invariants of the types it makes and the rules it uses, and
the validator is a function of its input, so a verdict is reused only where it
would be the same. A library's functions, met again in the next program, are
not checked again. A program's verdict is the first refusal in its order of
functions, as without the cache. Verdicts are also kept on disk under the
validator's build hash, and a function not known yet is checked under a lock
of its own, so processes that start together (the groups of the tests) check
each shared function once. A per-path thread mutex encloses the writable lock
handle within a process; the file lock still coordinates different processes.
The native List/Box helper units are lowered separately by `LibPackage`,
then linked and erased once by `MirHousekeeping`. Native code of the validator
itself is made with them, so they are built unvalidated, and the validator, once
built, validates them (`SelfHostedMir.encodeLibrary`: a List and a Box are the
structs they are, and the generic functions are checked as written, for any
type) before it is used (`ValidatorNative.validatorExecutable`). They are not user-facing
imports. `Pipeline` still checks their pre-erasure MIR before selecting them for
native lowering.

The CLI's package loader uses `Pipeline.loadFromFilesystem`, a `graph` load of the same snapshot. The parser executables (P1 from the current sources, P0 from its pinned seed; `TERSUS_PARSER=interpreted` runs the reference parser interpreter, `haskell` is refused) answer the file protocol for the parser's own tests and fixpoint, and P0 reads the compiler's own sources where the host still parses them. Single-file compilation rejects unlinked imports; the package pipeline resolves them.

   The rule of `lib/elaborate/libraries.tersus` decides which compiler libraries a program gets, from the program as read: the clone library (`lib/clone.tersus`: the trait `Clone` that `clone` calls, with its impls for lists, arrays and Boxes) unless the program declares a trait `Clone`, the equality library (`lib/eq.tersus`: the trait `Eq` that `=` and `!=` call, with its impls for lists, arrays and Boxes) unless it declares a trait `Eq`, the prelude (`lib/prelude.tersus`, embedded by `PreludeSource`: the traits `Sequence`, `Growable`, `Copy`, `Drop`, `Deref` and `Hash`, with `hashCombine`) when it mentions any of those names (or `hashCombine`) and declares none of the prelude traits, `lib/string.tersus` (the struct `String`, with `print`) when it writes a string literal or mentions `String`, `lib/map.tersus` (the struct `HashMap`) when it mentions `HashMap`, and `lib/set.tersus` (the struct `HashSet`, made of a map) when it mentions `HashSet` (declaring any prelude trait suppresses the prelude and with it string, map and set; a `HashSet` also pulls in the map library). The parser remembers the structs and enums declared so far, so a `match` becomes an `if` chain of `Is` tests (the last variant in the final `else`, its pattern fields read with `Project`), `x is V` the application of `Is V`, `x as V` the application of `Cast V` (whose input contract is `x is V`, and which returns its argument), a variant literal the application of its `Ctor` (named `Enum::Variant`), and a struct literal becomes the application of a `Ctor` builtin to the fields in declaration order, and `x.f` the application of `Field f`; the checker, evaluator and proof engine see structs as ordinary builtin applications. `//` line comments are skipped as whitespace. A call written as a statement (`f(x);`, `s.print();`) is an `Assign` to a name that no program can write (`$call L:C`, `callStatement`), so its result is not used. `Cli.runSourceWith input Interpret` gives the standard input (`readInputBytes`, as bytes) to `readByte` and prints what the program wrote with `writeByte` (`MirEval.runProgramWith`, decoded as UTF-8) before the value it returns. `for i in lo..hi` (outside a loop over the pack of a variadic function, which is a `PackLoop` of its own that each copy unrolls) has no node of its own: the parser (`forStatement`) turns it into assignments of `lo`, `hi` and `i` (the first two to variables named `$lo i` and `$hi i`, which `Pretty` shows as `(start of for i)` and `(end of for i)`) and a `While` over `i < hi` with `i >= lo` and `i <= hi` ahead of the program's own invariant, `shrinks hi - i`, and `i = i + 1` after the body. `for x in list` and `for i, x in list` are the same loop over `0..size(list)` with a hidden copy of the list and `Let x (get(list, i))` at the start of the body (`elementLoop`); the copy (`$list L:C`) and the index when there is no `i` (`$index L:C`) are named by the line and column of the `for`, so loops that nest or follow each other with the same names do not share them. `#[1, 2]` is the application of `ArrayFrom` to the list of its elements (a conversion that does nothing when it runs), and `Array<T, N>` the type `TArray T N`. `trait Name { fn f(...) -> T [{ in }] [{ out }]; }` is a `TraitDef`, and `impl Type { fn ... }` or `impl Trait for Type { ... }` an `ImplDef` that holds the functions it defines under the names `Type::f`; The functions of an impl are named `<Type>::f` or `<Type as Trait>::f` (`implFunctionName`); `Self` is read as the type of the impl (`declSelf`), and stays `Self` in a trait. `x.f(a)` is `F (Var ".f") [x, a]` until the checker knows the type of `x`, `Trait::f(x)` and `Type::f(x)` are calls of a name with `::` in it, and `<Type as Trait>::f(x)` a call of the function by its full name. `impl<T> Vec<T> { ... }` names the parameters of the impl after `impl` (`declImplParams`): every function of it gets them after its own type and size parameters, `Self` is read as the instance name of the struct with them (`Vec<'T>`, in `declSelf`, with the struct's fields registered under that name while the impl is read), and `Self::f` is the function of the base struct (`selfBase`).

The elaborator written in Tersus (`lib/elaborate/`, run as an executable through `ElaborateRequest`) infers and checks types (`a = b` and `a != b` in code are given the builtin comparison when the type is a word, `primitiveEq`, and are otherwise a call of the type's `Eq::eq`, with a `!` for `!=`, after the Boxes on both sides are unboxed so that a type that holds itself in a Box is compared by its own `eq`; in a `define` they stay the validator's equality; `impl Eq for T { };` reaches the checker as the impl the parser wrote out for it, `parser.standardEqText`, which compares the fields of the same variant and a list of the type itself element by element, with `shrinks self`) (unification inside a function body, with the declared parameter and return types and the builtin signatures) and resolves each `shrinks` clause by the type of its expression: an `Int` becomes `Counting` (at least 0 when an iteration starts, smaller when it ends) and an enum or struct becomes `Parts` (replaced by a field of itself), so the validator never sees `Shrinks`. The program is checked once, and the returns at the top level of a program have one type. It also takes traits and impls apart (`checkTrait`, `checkImpl`): a trait's types and contracts are checked with `Self` as a type with no fields; an impl's functions are checked as definitions at the top; for a trait impl they are compared with the trait's signatures with `Self` replaced, and for each trait function the checker adds a function named `Trait for Type::f` that has the trait's contracts and calls `Type::f` (`implCheckName`), so that the validator proves the impl meets the trait with no new reasoning. `inferExprR` gives back each expression with `x.f(a)`, `Type::f(a)` and `Trait::f(x)` replaced by the call of the impl's function (`resolveAssociated` looks `f` up among the impls of the type, in `tcAssoc`, and refuses a name that several define) for the type of `x` (or of the trait's `Self` argument), so nothing after the checker sees a trait, an impl or a method. `size`, `first`, `last`, `get` and `set` take a list or an array: `checkBuiltinCall` types the call from the kind of its first argument (and MirLower does the same when it replays the checker), so the validator and the later passes see one `Size`, one `Get` and one `Set` whatever the container, and an array's facts are a list's. `array(n, x)` needs a `n` that `constantInt` can fold to a number, which becomes the size in the type and replaces the argument, and an array may hold only `Int`, `Bool` and arrays (`plainElement`) and since it is held inline it can be a field of a struct or an enum and an element of a list (the native code lays out a field by the words of its type and a list by a stride of words, which the runtime also walks to clone, free, compare and print). The validator gets the size of every array local from its type (`SelfHostedMir.typeSteps`: at a parameter, an assignment, a call result and a loop head), so no contract has to say it. `Box<T>` (a struct or an enum held in a Box) has the value of what it holds: `Box::new(x)` and `Box::unbox(b)` become the MIR's `MakeBox` and `Unbox`, which the validator, the executor and the proof engine treat as the same value, a Box is looked into where a struct or an enum is (`fieldType`, `readField`, and the `is`, `as` and projection builtins by `checkBuiltinCall`), and `checkFinite` refuses a struct or enum that holds itself without a Box. A function can have size parameters (`fn dot<n>(a: Array<Int, n>, ...)`): its type is `TForall`, `genericCall` instantiates them with new unknowns that the arguments decide and writes the sizes as the last arguments of the call (a constant, or a size parameter of the caller), the sizes are Int parameters of the function that the body and the contracts can read, and the validator asserts `size(a) = n` for a local of type `Array<T, n>` (`withTypeFacts`). A parameter written `&T` has the type `TRef T` in the function's type (`checkType` refuses it anywhere else) and `T` in the function: `checkFunction` strips it (`unref`), `tcReadOnly` forbids assigning it, a call checks the argument against `T` (`checkCall`, `genericCall`), and MirLower marks the parameter in `fnBorrowed`. A Box holds any type that has a size, and an array of no size (`Array<T, ?>`) only behind one: `size`, `first`, `last`, `get` and `set` look through a `Box` of an array (`checkBuiltinCall`), `Array::boxed(n, x)` becomes `NewBoxedArray`, and `coerce` writes the unsizing conversion (the builtin `Unsize`) into an argument, a constructor field, a returned value or an assigned variable where a `Box<Array<T, N>>` is given to a `Box<Array<T>>`. The functions of an impl for a struct with parameters are generic functions named `<Vec>::push`: a call on an instance (`v.push(x)` with `v: Vec<Int>`) looks the function up by the base name of the instance (`ownerOfValue`), and `callResolved` instantiates it with `genericCall` like any other generic function; a trait implementation for such a struct follows the same generic mechanism. `clone(x)` and `x.clone()` are a call of the type's impl of the trait `Clone` of `lib/clone.tersus` (`traitArguments` says whether a type has one: a word, an address, a function and a reference are their own copy with none, an array, list and Box have one when their elements do, a struct or enum when an `impl Clone for T { };` says so, which `parser.standardCloneText` writes out as the impl that clones the fields, or when an impl with a body does); a value of a type made of a type parameter is cloned only where a `Clone` or `Copy` bound of the function says so (`unclonedParameter`), so a function written for any type clones none, except in the native list and Box helpers (`lib/lists.tersus`, `lib/box.tersus`, whose copies are native code's), where it is the builtin `CloneOf`, which the lowering turns into the MIR's `CopyOf` (the same value, which the validator and the executor take as a `Use`, and no impl runs for it). `impl Copy for T { };` needs the type to be Clone (`checkMarkerImpl`, as it checks the fields are Copy) and gives back a `CopyDef T` statement for the lowering. A bound `T: Clone` or `T: Copy` is met by `traitArguments`. `array(n, x)` and `Array::boxed(n, x)` need the type of `x` to be Clone, and a struct update `..clone(base)` is written by the parser as a `clone` of each field that is not given. A function with bounds on its types (`fn total<S: Sequence<Int>>`, a `BoundedDef`) has its signature and bounds checked where it is written, and its body is checked once against its bounds alone after the module's statements are (`checkDefinitions`: each bound `T: Tr` stands for an impl of `Tr` for `T` whose functions are `<$param T as Tr>::f`, and a call of another function with bounds needs only its bounds met; so are the functions of a bounded impl and the checks of a bounded trait impl's functions), and given back with its type parameters, after the module's statements; each call decides the types, checks them against the bounds (`traitArguments`: a list, an array and a Box of an array implement `Sequence` and `Growable` as built-ins, a struct what its impls say) and names the copy for them (`total[Vec<Int>]`, an `Instance` record), which the copy step makes from the lowered body when the program is linked (`MirCopies`, MIR.md "The copy step"), so validation and everything after it never sees a bound. A variadic function's pack (`args: &..T`) is checked the same way, with `size(args)`, `get(args, e)` (the index fixed in each copy), the loops over it (`PackLoop`, which the parser writes for a `for` over the pack) and its contracts given types of their own for its elements, and a call checks each trailing argument against the pack's bounds (`templateCall` over the template `packTemplate` makes for the number of arguments).
3. `MirLower.lowerElaborated` lowers the checked program to the MIR of `Mir.hs` (see MIR.md): a `Program` of typed functions, each a map of basic blocks of simple statements ending in a terminator (`Goto`, `SwitchBool`, `Call`, `Return`, `Unreachable`). Lowering resolves the scopes to numbered locals, turns `if` into a switch whose branches meet at a join block (a condition made of `&&`, `||` and `!` is a switch for each of its tests, `lowerCondition`, and a Bool value made of them is the same tests ending in two blocks that assign `true` and `false`; a `while` records the first block of its body, `loopBody`, where the validator starts an iteration) (none when both return, and statements after a `return` are not lowered, so they are not validated either), `while` into a header block that the end of the body jumps back to, nested expressions into temporaries, a call into a `Call` terminator, builtins into `BinaryOp`/`ListOp`/`MakeData`/`ReadField`/`IsVariant` rvalues (`as` is `AsVariant`: the same value, typed as the variant), and lifts a function defined inside another to the top (`outer::inner`; a builtin used as a value becomes a small function of the program too). The AST has no types, so `elaborate` hands the lowering the type of every expression, fully resolved (the unifier that decides `x = []`'s element type from a later `push` has already run), in the order the lowering visits them, and the lowering gives every local the type of the expression that made it; a type no use decided is `Int`. The contracts, loop invariants, `shrinks` clauses and `affirm`/`define`/`rewrite`/`axiom`/`proof` statements are kept in the MIR as `Ghost` statements and a `FunctionSpec`, which the executor skips. Each is written with the names of the source, so it carries an `Env`, what each name stands for at that point (a local, or a function), and `GhostFunction` marks where a function is defined. `lib/mir/mir_verify/mir_verify.tersus`, run on the MIR as data by `MirHousekeeping`, checks that the result is well formed (every jump goes to a block, every local is declared and typed, and every operation is applied to operands of the types it takes) and lowering fails otherwise. A `Mark` becomes a `GhostPosition` statement (and is written again at the start of each block), `CopyDef T` (which the checker writes for `impl Copy for T`) is collected, and `MirMoves.checkMoves` then follows the places that are moved out (a local with the fields and elements followed from it) along every path of each function, with the views that a field, an element, a cast, a `Box::unbox`, a `match` and a `for` make of the place they read, and reports a use of a place after it was moved, a move out of a list or of a lent parameter, and a place that one call or assignment both lends and moves, or lends and moves a value that holds it or a part of it (`f(s, &s.xs)`, `f(s, s.xs)` with a lent second parameter, `W { s: s, r: &s.xs }`), with the line and the name (`Lowering failed: Move error: in f, line 9:5: ...`); `stripPositions` takes the places out of the MIR it gives back. `lib/lists.tersus` and `lib/box.tersus` are lowered with the same check (`lowerLibrary`).
4. The validator is a Tersus package, `lib/validation/` (embedded by `PreludeSource.validationPackageFiles`), linked once without itself being validated. Its sole `driver.tersus` entry imports fourteen declarative sibling providers in the same root module: the data model, relations, differences, context and linear reasoning, sequence facts, goal proofs, state and joins, evaluation and execution, saturation, loop inference and flow. Each file imports its actual providers explicitly; native and reference construction use that same package entry, without assembling source text. Reference queries call named core functions and never run the driver main. The entry module keeps bare core identities; its bounded helpers use the same ordinary checked-template interface as imported project modules. It is the bootstrap, and the checked native executable is published only after it proves its complete source and physical native List/Box storage. It is compiled to native code once and kept in the cache directory (`ValidatorNative`, with `lib/validation/driver.tersus` as its main program), and that program is what validates every program; the interpreted validator remains only where the validator is itself the program under test. `SelfHostedMir` translates the MIR into the validator's data: each function becomes a list of `ExecutionBlock`s (statements as `ExecutionStep`s over numbered terms, terminators as `ExecutionEnd`s, contracts and loop invariants as check and assume steps), and `validateExecution` sweeps them. Anything the translation does not model (an extern function, an address, block or fixed-width-word operation, a function value it cannot resolve) refuses the whole program: `the program uses a feature the Tersus validator does not model yet: <what>`, naming the part it does not model. There is no other validator to fall back to. The driver reads that data strictly: a step, end or value reference it does not know, a record whose fields are not the ones it reads (one missing or extra, or one of another kind than it reads: an integer, a Bool, a value reference or a list, and a list of integers or references holding anything else), or a value it cannot parse becomes an unsupported step or end, and an entry state holding such a record refuses its function; the validator refuses rather than misreads. A path through a function is an `ExecutionState`: the term each local holds and a `ValidatorContext` of facts. A block's steps run in turn: an operation records what it establishes (a `push` its new size and element and the reads it keeps, a `get` the element it read, a checked assertion the relation it proved); a call checks the callee's input contract and assumes its output contract, the body neither run nor read for facts. `affirm`, `define` and `rewrite` see the values the locals hold where they are written. A `SwitchBool` delivers each way with the condition's truth added, and the relation it compares when it is one, negated on the false edge; where the branches meet again, the states that arrive are joined (`mergeArrivals`): a local bound to different terms gets a fresh one, the facts from before the branches parted are kept as they are, and of what the paths added what survives is what both establish, rewritten to the joined terms, plus the weaker of the two paths' constant bounds and offsets, and a block runs once on the result (a return or a latch runs once per arriving state, and an empty forwarding block passes each on unchanged). A loop's invariant is checked on entry, the locals its region assigns are replaced by fresh terms with the invariant and the condition assumed, and each edge back to the header must establish the invariant again and shrink the variant; the loop is left from the header and from the false edge of each later `&&` conjunct, with nothing re-assumed on the latter; a function that calls itself must say why it ends (`shrinks e`, or `~` for one that may not), and a loop or call that may not end is refused where termination is required. `axiom` and `proof` declarations register validation-only rewrite rules. A struct's invariant is checked where a value of it is made and assumed of every value of its type; a `Byte`'s value is known to be from 0 to 255 wherever it came from.
5. The validator decides what the facts of a state entail (`entailsGoal`), and a check asks only about the facts near its goal: a walk from the goal's terms over an index of the block's facts by term, charged for each fact it looks at and each term of a fact it keeps, at budgets of 64 to 1024 units and at most 8 steps out, that reaches constants without walking through them and keeps a hub without expanding it (`goalSlice`, `checkInSlices`). Saturation, case splits and the flow's own queries run on that slice; a goal that reads a list or a block also follows the chain of writes behind it (`chainSlice`), and the terms they make are new to the whole state. A check admits at most 3,008 units. The other questions a step asks (a term's value or sign, what a list is made of and what is read of it, whether an application is already made or a result term is taken) go to the same index: the applications on a term's first 64 links, and slices up the same ladder, so a step costs a bounded amount however long the function is; where the answer lies beyond them it is not known, which can only refuse. A term a step mints is below the state's floor, an id at or below every id the state mentions, which each mint lowers and a join takes the lower of. A sweep runs every block on one state, its trunk, and keeps a state that waits at a block as a mark on the trunk and the facts and locals it has beyond it: a fork costs what its arms add, an arm is undone by cutting the trunk back to its mark (and the index with it), and a join renames and intersects only what the two paths added. The index follows the trunk across blocks, forks and joins rather than being built for each block, and a `forall` check's body runs on the state and is undone the same way. A fact is copied again only when the trunk is cut below a state still waiting that holds it, once per enclosing branch. Filtering inferred loop invariants still grows with the facts of a function. Code after an assumption that its nearby facts contradict is not checked. The search is bounded, sound and incomplete: what it cannot prove is rejected with the clause in the words it was written in (`Could not prove: x > 0 (in f)`: the bridge keeps each check's clause beside it, off the data the validator reads, and looks it up by the block and step the validator names), and the program adds `affirm`s, `define`s and `rewrite`s until it can (see LANGUAGE.md). A congruence closure over the known equalities makes equal arguments give equal results without any rewriting, and difference constraints over its classes decide integer comparisons, so `s = 3` gives `s > 0` and `i < n` gives `i + 1 <= n`; a disequality strengthens a bound between its terms to a strict one, and an order scales by a known factor. What differences cannot decide goes to linear arithmetic over the facts of the slice (a sum, a multiple, and division or remainder by a constant become identities between their terms): the facts together with the negated goal must have no whole-number solution, which Fourier-Motzkin elimination decides, dividing each derived inequality through by the gcd of its coefficients, so `2 * i = 2 * j + 1` is already a contradiction. A `forall` goal is proved for a fresh index meeting its guards, and `forall` facts are instantiated at the elements the program reads. A proper-part claim (`Within`) holds when the first term is reached from the second by field reads.   After validation `lib/mir/mir_erase/mir_erase.tersus`, run on the MIR as data by `MirHousekeeping`, takes the permissions (`Block<T>`, the ghost values of POINTERS.md) out of the program: their locals, parameters, fields and operands, and the ghost operations that make them. Nothing after it (the executor, the ownership pass, the lists of native code, `MirData` and both emitters) sees one. Before validation, `MirMoves` has checked that every permission is used exactly once.
6. `MirEval.runProgram` runs the MIR: it keeps the locals of the function in a map and the block it is in, runs the statements, then follows the terminator (a `Call` runs the callee and stores its result in the destination), and still reports `Division by zero`, `Get index out of range` and the like, which validation is meant to make unreachable. `Int` is 64 bits and arithmetic traps on overflow (`Integer overflow`). Lists and arrays use immutable indexed sequences: length and endpoints are constant-time, while indexed reads and updates are logarithmic. Updating a sequence preserves older values and borrowed-place writes still update the caller's frame. Calls with fully known reference-free parameter contents and results do not traverse those values to rebase references; reference-bearing and unknown types retain the full reference handling. For finite, fully-defined list spines, the host's `MList` construction, matching, equality and rendering are unchanged. `renderProgram` prints the MIR.

7. `Pipeline.nativeProgram` expands reference writes, then `MirLists.lowerLists` replaces logical List/Box operations with calls to the native helper units. `LibPackage` has the elaborator read the embedded `tersuslib` sources and lowers `lists` and `box` separately against the `types` and `prelude` interfaces their sources import. `types.tersus` is the only declaration of the structs and their physical layout invariants. `MirHousekeeping` links the helper units and erases each unit's permissions; the validator, built with them unvalidated, validates them with their physical layouts before it is used. These bodies and native Drop impls are never selected as user-facing implicit libraries.

   Native lowering links only the required erased units through `Link.linkPrograms`; it adds nothing when there is no storage to lower. Bare type identities and helper symbols stay unchanged: `List<T>` has `addr`, `len`, `cap` in that order; `Box<T>` has only `addr` at runtime. List construction, push, set and pop use `listNew`, `listPush`, `listSet` and `listPop`; scalar Box allocation and unboxing use `boxNew` and `boxUnbox`. Reads retain their direct layout operations. A Box of an array uses List storage, including `listFilled` for `Array::boxed`. `MirMono`, ownership, drops, clones, the emitter, ABI and MIR wire formats retain their existing behavior. Inconsistent copies of one unit identity and user/helper symbol collisions are link errors, not left-biased merges.

The CLI in `app/Main.hs` drives these paths over a source file (logic in `src/Cli.hs`):

- `stack run -- check <file>` parses the program, lowers it to the MIR and validates that, printing `OK` on success.
- `stack run -- run <file>` validates the program, and only if that succeeds compiles it to native code (the lowering and LLVM path of `build`, so it needs `clang`), runs the executable and prints its return value (nothing is printed when the program does not `return`). The executable is removed afterwards and its exit status is the one of `run`.
- `stack run -- eval <file>` validates the program and runs its MIR with the reference interpreter (`MirEval`), which needs no compiler. It is what native code is tested against, and not the way a program is run.
- `stack run -- mir <file>` validates the program, and only if that succeeds prints its MIR.
- `stack run -- owned <file>` validates the program, and only if that succeeds prints the MIR that native code is made from, with the moves, copies and frees (the ownership pass, `lib/mir/ownership/`).
- `stack run -- mir --data <file>` prints that MIR as data, in the line-oriented format of `MirData` that a program can read (what the emitter in Tersus of step 31 is given, see `STEP31.md` and MIR.md, The MIR as data); `lib/mir/mir_reader/mir_reader.tersus` reads it from the standard input into the types of the MIR, written in Tersus, and writes it again (`tersus mir --data p.tersus | tersus run lib/mir/mir_reader/mir_reader.tersus`); `stack run -- mir --ghost-data <file>` prints the MIR before its ghosts are erased instead (version 2 of the data), which `lib/mir/mir_erase/mir_erase.tersus` erases and writes as version 1, and `lib/mir/emit/emit.tersus` is the lowering to LLVM IR written in Tersus, which writes all of the IR of a program (`tersus mir --data p.tersus | tersus run lib/mir/emit/emit.tersus`; the arguments `outline` and `bodies` write the parts it was written in).
- `stack run -- llvm <file>` validates the program, and only if that succeeds prints its LLVM IR; `stack run -- build <file> -o <output>` compiles that and the C runtime (`LlvmRuntime`) with clang (`Native`). Native code handles every type of the language. The IR is written by the emitter in Tersus, `lib/mir/emit/emit.tersus` (step 31, `STEP31.md`), the compiler's only emitter. It is built with clang the first time it is used, in two stages (`Bootstrap`): the seed, the IR of an emitter that is a GitHub release asset pinned by `bootstrap/emitter.sha256` (fetched and verified on first use; a seed at `$TERSUS_SEED_FILE` or `bootstrap/emitter.ll` is used instead when present), is built (stage 0), and it compiles the emitter as it is now (stage 1). Both are kept in the cache directory of the user (`$XDG_CACHE_HOME/tersus`, or `~/.cache/tersus`), named by a hash of what they are made of, so the first `build`, `run` or `llvm` takes about a minute and a half and the next ones do not.
- `stack run -- assumptions <file>` prints what the program takes on trust, which the validator does not prove: each `assume e;`, `Block::assume(p, n)` and `axiom`, with its line (`Pipeline.assumptionsOf`), or `No assumptions`.
- Use `-` as the file to read the program from standard input.
- Errors go to standard error, prefixed with `Parse error:`, `Validation failed:`, `Lowering failed:` (a bug: a program that type checks always lowers) or `Evaluation failed:`. The exit code is 1 for a failed program and 2 for bad command-line usage.

15. `&&` and `||` in conditions
    Done: a condition (and a Bool value) can combine tests with `&&`, `||` and `!` (LANGUAGE.md, Connectives). 16. Conditional contracts

17. LLVM
    Validation runs the Tersus validator over the MIR, and the AST has no evaluator any more: the MIR executor runs programs. The MIR is lowered to LLVM IR (the emitter written in Tersus, MIR.md, Native code) in steps, each checked against the executor by building and running programs:
    1. Done: `Int` and `Bool`, control flow, calls and recursion, the overflow traps, and the printing of the result
    2. Done: lists, with a runtime of C (`LlvmRuntime`): literals and operations, structural equality and printing by a descriptor of the type
    3. Done: structs, enums and function values: every example builds natively and prints what `tersus eval` prints
    4. Done: memory (`lib/mir/ownership/`, MIR.md, Ownership): every value of the heap has one owner, the last use of a local moves the value out of it, a value that is wanted twice is copied, values are freed when their owner lets go, and `push`/`set` change the list in place; a list built by pushing takes time and memory in proportion to its length
    5. Borrowing a value to a function that only reads it, so that a call does not copy an argument that is used afterwards
        Every parameter is owned today (MIR.md, Ownership), so `helper(l, i)` called again and again on a list that is used afterwards copies the list at each call, which makes a loop of such calls take time in proportion to the square of the length. The pass already decides move, copy or look per operand, so a borrowed argument is a fourth outcome, plus an inference of which parameters of a function it only reads (a fixpoint over the calls: a parameter is owned if some path moves it, or passes it where it is owned)
        What needs care: a function reached through a function value (its convention has to be one for every function, or a small wrapper made when a function is used as a value), a value passed both borrowed and owned in one call (the owned one has to be a copy), and the check of the result by the model of the heap (`TestOwnership`), which has to learn what a borrowed parameter may do
    6. Deep recursion and deep values
        Native recursion uses the C stack, and freeing or copying a very long recursive value (a million-node list built of an enum) recurses too, so either could overflow it, where `tersus eval` has no such limit. An iterative free and copy, and a bigger stack or a clear error when it runs out, would fix both
    7. Contracts as hints to LLVM
        The code assumes what validation proved (a divisor that is not 0, an index in range, a list that is not empty) without checking, but LLVM does not know the proofs, so it cannot drop the work around them. Emitting `llvm.assume` for the facts that justify each `get`, division, `first` and `last` could let it. A mistake in the validator would then be wrong code that the optimiser has built on, so it needs the memory and answer checks of the tests to run with the hints on
    8. Cheaper ownership
        A part that is kept (`row = get(rows, i)`) is copied, and so is the inner list of `rows = set(rows, i, push(get(rows, i), x))`, which costs the size of the inner list where a move out and back in would cost nothing; a field update through `..p` copies a list field unless `p` is dead; a value that is read for the last time is only freed when its local is assigned or the function returns; and only temporaries can look at a value, not named locals that are only read
    9. Run the valgrind checks in CI
        `testNative` runs some programs under valgrind when it is installed, and the CI runner does not have it, so there only the checks of the runtime (`-DTERSUS_CHECK`) and the model of the heap run. Installing it in the workflow would keep the independent check
21. Generics over traits (done in the form of a copy of the function per type; the modular form is planned, see 24)
    A function can take "any type that implements a trait": `fn total<S: Sequence<Int>>(s: &S) -> Int` (LANGUAGE.md, Bounded types). The bound is a `BoundedDef` that the parser writes; the body is checked once against its bounds alone where it is defined (only the functions of the written bounds, and `clone` with a `Clone` or `Copy` bound, on a value of a type parameter, which a function without bounds never clones; a call of another function with bounds needs only that the caller's bounds meet the callee's), given back with its type parameters, lowered once and checked for moves once. Each call decides the types by unification, checks each against its bounds (`traitArguments`: a list, an array and a Box of an array implement `Sequence`, a list also `Growable`, a struct what its impls say), and names the copy for them, `total[Vec<Int>]`, which the copy step (`MirCopies`) makes from the lowered body when the program is linked, a call through a bound made the call of the type's impl. An impl with bounds (`impl<K: Hash, V> HashMap<K, V>`, `impl<T: Same> Same for Pair<T>`) is a function with bounds for each of its functions, and a function of an impl of a type may add bounds of its own (`fn with<U: Size>(self: &Self, u: &U)`), which follow the impl's (the parser leaves such a function under its bare name, and the elaborator names it `<Pair>::with` when it reads the file, `load.implBoundedNames`); for a trait impl the type implements the trait for the types that meet the bounds (`tcImplBounds`, read by `traitArgumentsOf`), and the function that checks each impl function against the trait is copied together with it. So the validator, `MirMono` and native code have no bounds and no change, and a contract of the function is proved for each type. What is chosen for now: a call of itself must give its own types or smaller ones (the copy step refuses a copy for a bigger type than the copy that needs it, so the impl for `Pair<Pair<Cell>>` can call the one for `Pair<Cell>`), and the types of a call cannot be made of a type parameter of the function that calls. The modular form (validate the body once against the trait's contracts, with a placeholder for the trait's functions on the type parameter and the call sites substituting them) is step 24. A function with bounds can also be variadic (`fn total<..T: Measure>(args: &..T)`, LANGUAGE.md, Variadic functions): its pack of types is checked once with an opaque type for each element, each call is checked argument by argument against the pack's bounds and names a copy for its arguments' types (`total[Int, Bool]`), and the copy step first expands the pack (`MirPacks`: one parameter per argument, `size(args)` a number, `get(args, k)` the parameter at `k`, loops over the pack unrolled, branches the copy does not take dropped, an index out of range a proof obligation). Not yet: giving a pack, or a slice of one, to another function.
    The functions that check an impl against its trait are the obligations a generic function relies on. What is still missing is that a trait cannot say that its functions end (an impl may be `~`), which a generic function that relies on termination would need
22. More of traits and impls
    Impls written for `Int`, `Bool` and lists (`impl Measure for List<Int>`; a list, an array and a Box of an array already implement `Sequence` and `Growable` as built-ins that `traitArguments` knows by name, which a program's own trait of the same name and one type would also get), default bodies in a trait (a default has to be validated for every `Self`, so it needs the generics of step 24), a trait that names other traits it needs (a trait can already call the functions of the traits declared before it on `Self`, as `Growable` does `size`), traits with sizes, associated constants and types, type parameters for an enum and for a function of a trait impl, a bounded function as a value, and bounds of its own on a function of an impl of a trait (a function of an impl of a type can have them). The functions that check an impl are compiled into the executable although nothing calls them; they could be left out of the MIR after validation
24. Generic validation of bounded functions, and the list facts on the traits
    Two steps that belong together. (a) A function with bounds is validated once, against the contracts of the traits, instead of for each type (step 21 copies it): a call of a trait's function on a type parameter (`size(s)` for `S: Sequence<Int>`) is a placeholder `<S as Sequence>::size(s)` whose promises are the trait's elaborated contracts; the call sites substitute the placeholder with the function of the type they give (`MirMono` already finds the types of a call), and the executor dispatches the placeholder on the value. That lets a function with a type parameter of its own call one with bounds, makes the body unable to use more than the bounds say, and lets a bounded function be in an impl or a value. (b) The proof engine's facts about lists (`size(push(l, x)) = size(l) + 1`, `get(set(l, i, x), i) = x`, the frame of `pop`) are the `forall` facts of the contracts of `Sequence` and `Growable`, instantiated for calls of the trait's functions, so the builtin overloads of the checker and the engine's list knowledge go and a list is a library type in the validator as it is in native code.  The MIR would need the bounds of a function (`fnBounds`) and which parameter of a trait function is `Self` (`progTraitFns`).
25. Raw pointers, with manual allocation and drop (done: POINTERS.md, Status)
    Today ownership is implicit: the ownership pass (`insertOwnership`, `lib/mir/ownership/`) decides every `Move`, `CopyOf` and `Drop` of a value that `needsDrop`, and a program cannot say where a value is freed or point at one without owning it. The design is `POINTERS.md`. A pointer is two values: an address `Addr<T>`, a runtime word that can be aliased, offset, kept anywhere and passed to C, and a permission `Block<T>`, a ghost linear value that `Addr::alloc(n)` returns with it and that every operation on memory needs (`Addr::get(p, i, b)`, `write`, `take`, `dropValue`, `dropRange`, `resize`, `free`). The permission names its memory (`base(b)`, so the address given must be its own) and says what the memory holds as two ghost arrays indexed from 0 (`filled(b, i)`, `at(b, i)`), so a write is `set` and what the validator knows of arrays carries over, with no heap model. It is linear, so two permissions never overlap and nothing has to prove that addresses differ, and a block knows its allocation (`origin`, `whole`) so that `Block::split` and `Block::join` cannot free memory twice. Bounds, reads of written slots only, no use after free, no double free and no element lost when a block is freed are then proved in ordinary code, which needs no mark: what is unsafe is an assumption (`assume e;`, `Block::assume(p, n)`, the contract of an `extern fn`), and `tersus assumptions` lists them. It needs tuples (an operation gives an address or a value and a permission), linear types (step 27), ghost locals, parameters and fields (erased after validation), and a layout in bytes (an 8-bit `Byte` and `Bool`, the fixed-width integers `I8` to `U32`, and C's rules for structs), and it comes with `Uninit<T>`, a slot that may hold nothing, for collections that need no addresses. The first users are `Buffer<T>` and `examples/vec.tersus`, written on an address and a permission and not on `Box<Array<T>>`. Built (POINTERS.md, Status): tuples (`TupleN` structs of the language), `Addr<T>` and `Block<T>` with every operation of the table and `Block::split`, `join`, `cast` and `assume`, the ghost functions (and `count(b)`, which `free` asks to be 0), the linear check of permissions in `MirMoves`, their erasure after validation (`lib/mir/mir_erase/mir_erase.tersus`), a heap in `MirEval`, both emitters and the runtime (`tersus_addr_alloc`, `tersus_addr_resize`, `tersus_addr_free`, `tersus_drop_slots`), `assume e;` and `tersus assumptions`, and `examples/addresses.tersus` (a buffer, a `Vec<T>`, a buffer split between two functions and a list in an arena). Also built for it: `linear struct` and `linear enum` (what step 27 describes, with the check of moves), `Uninit<T>` and `replace`, `extern fn`, the fixed-width integers `I8` to `U32`, and the layout in bytes (C's rules for structs, a `U32` tag for an enum, 1-byte `Byte` and `Bool`) in both emitters and the runtime. The list of native code, `StdList` of `lib/lists.tersus`, is an address and a permission with the invariant of a `Vec`, proved with the contracts of the operations on memory. A user-defined drop (step 26) is built too: `impl Drop for T` with `fn drop(self: Self) -> Int`, with which a type that holds a permission is freed where it goes out of scope instead of being linear (`examples/drops.tersus`). And the native part of `Box` on an address (step 29): a `Box<T>` that is not of an array is the struct `StdBox<T>` of `lib/box.tersus`, one slot at an address with a drop, in native code, as a list is a `StdList`; what is left of step 29 is the language items
26. User defined drops (done: POINTERS.md, Status 9)
    `impl Drop for T { fn drop(self: &mut Self) ... }`, a trait that the ownership pass calls where it now emits a `Drop` of a struct, and the way a type that holds a raw pointer (step 25) frees it. What it takes: the ownership pass asks "does the type have a drop, or hold something that does" in `needsDrop` (a struct with a drop is never plain, whatever its fields are) and emits a call of the impl's function before the fields are dropped, in the order of the fields; `Drop` of a moved-from value is not emitted, which needs drop flags in the MIR for a value that is moved in one branch and not the other (today the ownership pass inserts a `Move` and a `Drop` per path and needs none); a copy of a type with a drop is its `Clone` or an error (`Clone` and `Copy` exist, and a type is not Copy unless it says so), since a bitwise copy would free twice; a drop may not fail or end late (it is a function that ends, which the termination checks already say, and its contract is that it frees what the value owns); and the validator needs the drop to be a call it sees, because what a program proves about a value must not depend on a free that happens at the end of a block. `Box<T>` and lists keep their drops in the runtime until the library versions of step 25 replace them. Built (POINTERS.md, Status 9): the drop takes `Self` rather than `&mut Self`, so that it can use the permission it holds, and the runtime frees what the fields own after it; a value is taken apart without its drop by `T { f: x, ... } = v;`, a type with a drop is not linear and not copied, and a value that was taken apart is told by the bytes that were cleared, and a local that was moved from is not dropped at all (the ownership pass works that out from the flow of the program, with a flag local for a value that is moved on one path and not another), so a type with a drop holds a permission (whose address is never 0); `Box<T>` and lists are freed by drops of the library (`examples/drops.tersus`)
27. Linear types
    (Copies are explicit now: a value that is not Copy is moved, `clone(x)` is a copy, and `MirMoves` follows the places that are moved out along every path and reports a use of one, which is the half of this step that tells a value that was moved from one that was not. What is left is the rule that a linear value has to be moved on every path, the obligations of `DROPS.md`, Part 2.)
    A value that must be used exactly once: a `linear struct` (or a `linear` mark on a type) that cannot be dropped without being consumed, copied or ignored, and is passed on, returned or consumed by a function that takes it by value. It is the guarantee that a handle (a file, a lock, a pointer from step 25, an in-flight request, a value that has to be closed) is not forgotten, and the other half of step 26: a drop is the implicit use of a value at the end of its scope, and a linear value has none, so the checker reports a linear local that is still alive at a `Return` or at the end of a block (`x is linear and is not used`), and a use after the use (`x was moved`). The checker needs the flow the ownership pass has (which locals are live at each point of a block; the ownership pass has it for lists), so it is written over the MIR and its basic blocks and not over the statements, and a branch has to use the value on every path or on none, a loop body may not consume a value of the loop that it did not make, and a function that may not end (`~`) is allowed to leave one, since it never reaches the end. The validator gains a small fact: a linear value is used once, so what a contract says of it before the use cannot be said after, which the rename to a new value (`x2 = close(x)`) already gives. Affine (at most once) is the same check without the leftover rule and is the first step; `linear` adds the leftover rule, and a type with a drop is affine
28. Preparing for async / await
    Nothing in the language is asynchronous, and the design is not chosen. What is true of the MIR is that it suits it: a function is a map of basic blocks that end in a terminator, so a suspension point is a `Call` that may not return at once, and the frame (the locals, `fnBorrowed`, the slots `alloca`ed in the entry block) can be turned into a state that the function keeps while it waits, as Rust's generators are. The steps that prepare for it, none of which needs `async` in the syntax: (a) a trait `Future<T>` with a `poll` (or a `Task`/`Waker` pair) that an `impl` can give, so a runtime is a library; (b) lowering a function with suspension points to a state machine in the MIR (`MirCoroutine`, after validation and before ownership, like `MirLists`), with the locals alive across a suspension as fields of the state; (c) the rules that make that safe, which are exactly the ones of steps 25 to 27: a borrow (`&T`, which only a parameter has today) may not be held across a suspension unless the state owns what it borrows, a raw pointer in the state is the program's responsibility and a linear value in the state must be used when the future is dropped or cancelled (so a drop of a future is a cancellation, and runs the drops of the locals alive at its suspension point); (d) what the validator proves across a suspension: the facts of a local survive it, the facts about anything shared do not, and a contract of an `async` function is about the value it finally gives; and (e) the termination checks: a loop that awaits is not a loop that shrinks, so `shrinks` needs a reading for it (or `~`) and a call of `await` in a function that has to end is allowed only on a future that is known to. Strings, input and output (step 20) give a program something to wait for, so they come first, and the order of this block is 25 (pointers), 26 (drops), 27 (linear types), then 28 on top of them
29. `Box` defined in Tersus, and no special cases left in the compiler (in native code, done: POINTERS.md, Status 10; the deref and the traits of a list are done, POINTERS.md, Status 11; the types themselves are structs of the library now, and what is left is their operations and proof facts)
    After steps 25 and 26 a `Box<T>` is a raw pointer that owns room for one `T` and frees it in its drop, so it can be a library struct (`struct Box<T> { addr: Addr<T>, ghost blk: Block<T> }` with `impl Drop`, `new`, `unbox`, and the deref the language gives every smart pointer; `POINTERS.md`, The library on top) the way `StdList<T>` is already. What the compiler does for `Box` by name today, which has to become the library's or a general rule: `TBox` in `Type` and `MakeBox` and `Unbox` in the MIR; reads of a field, `match` and the builtins of arrays through a Box "transparently" (the checker looks through it, `Box::unbox`), which becomes a deref rule that any type with a `Deref` impl gets; the check that a recursive type has a `Box` in its recursion (`checkFinite`), which becomes "a recursive type goes through a type of known size, such as a pointer" and is asked of `Addr<T>` and not of a name; the fat `Box<Array<T, ?>>` (two words, kind 7 in the runtime, `Unsize`, `NewBoxed`, `Array::boxed`, `Array::empty`), which becomes a `Buffer<T>` with a length (`POINTERS.md`) and its coercion from a `Box<Array<T, N>>`; and the runtime's clone, free, compare and print of a Box by descriptor, which become the impl's `Clone` and `Drop` and the derived equality and printing of a struct. The same pass over the rest of the list of things the compiler knows by name: `List<T>` as a builtin type (`TList`, `ListOp`, the overloads of `size`, `get`, `set`, `push`, `first`, `last` and `pop` in `StdLib`, and the proof engine's list facts: steps 7(c) and 24; `MirLists` and `Variants.tagged == 2` for printing a `StdList` stop being needed when `List` is a library struct of the prelude); `Array<T, N>` (`TArrayOf`, `NewArray`, `ArrayFrom` and the `#[...]` literal), which stays a builtin of the language as the inline array and is the one type the library cannot make; the traits that `traitArguments` gives lists, arrays and Boxes by name (`Sequence`, `Growable`), which become impls in the prelude; the methods of `listMethod` and `sequenceFunction`, which become the general call of an impl's function; the reserved names (`StdList`, `stdList...`) that stop a program from using the library's; and the builtin names that a program cannot define (`size`, `first`, ... and `pop`). The test of being done is that the compiler's source mentions no library type by name (`Box`, `List`, `StdList`, `Vec`) except where a language item is declared (`#[lang = "box"]`, for the allocator, deref and the unsizing coercion that no library can write), and that `lib/` and `examples/vec.tersus` are the only places those types are defined. The order is: pointers and drops (25, 26), the proof facts on the traits (24), `List` as a prelude struct (the case where nothing is lost: it already is one natively), then `Box`, and last the language items that are left. Built so far (POINTERS.md, Status 10): native code makes each `Box<T>` that is not of an array the `StdBox<T>` of `lib/box.tersus` (an address and a permission, proved, with a drop), and each Box of an array a `StdList<T>`, so the runtime no longer allocates, frees, copies or compares a Box of its own; the recursion check accepts an `Addr<T>` as it does a `Box`. Built since (POINTERS.md, Status 11): the look-through is a general rule, a `Deref<T>` impl that any type can give (LANGUAGE.md, Deref), which the checker applies to a field, `is`, `as`, a `match`, the base of an update and `shrinks`, in code and in proofs, with a Box as the one Deref the language gives itself; and an impl can be written for a `List<T>`, a `Box<Array<T>>` and an `Array<T, n>`, with `lib/prelude.tersus` declaring `Sequence` and `Growable` for a list and `Sequence` for an array and a Box of an array, which `traitArguments` reads where an impl is declared. The types themselves are structs now: `lib/types.tersus` declares `struct List<T>` and `struct Box<T>` (the fields and invariants the native forms have), every program has them in front of it unless it declares a type of one of those names itself, and in the checker a list or a Box is a named instance (`TNamed "List" [ArgType t]`), so a use whose element type is not known yet carries that unknown in its argument and is decided by inference as any other struct is (the `TList`/`TBox` patterns in `Types` are how the rest of the compiler speaks of those two instances). What is left: `MakeBox`/`Unbox`/`Unsize` and the list operations are still operations of the MIR with the facts of `lib/stdlib.tersus` behind them, so the proof facts of a list are not yet the facts of the `Sequence`/`Growable` traits (step 24 (b)); `=` on two Boxes is equality of what they hold, and the unsizing coercion and `Box::new`/`Box::unbox` are the language items a library cannot write; and the native forms are still named `StdBox`/`StdList` for the runtime and the emitter
30. Less C: the runtime written in Tersus
    `LlvmRuntime` is about 260 lines of C that the emitted IR calls, and everything in it is either something Tersus will be able to say once steps 20 and 25 to 29 are done, or one of a few things only the operating system can do. The pieces, with what replaces each: (a) `tersus_drop`, `tersus_clone` and `tersus_print`, which walk a `Type` descriptor at run time, become code made per type (equality is done: `=` is the trait `Eq`, whose impls are Tersus, and `tersus_equal` is gone): the ownership pass and a derive step emit a `Drop`, `Clone` and `Display` impl for each struct, enum and array in the program (the same monomorphization `MirMono` does for generics), and the descriptor tables (`Type`, `Variants`, `ArrayInfo`, `KIND_*`) and the `tagged == 2` case for `StdList` disappear; (b) `tersus_box_new` and `tersus_box_free`, `allocate`, `release` and `reallocate` become the library `Box` and list of steps 25 and 29, on a raw pointer, over two or three built-ins for memory (`alloc`, `realloc` and `free`, which the emitter turns into calls of the system's allocator, or `mmap` and `munmap` if the program is to link nothing); (c) `TERSUS_CHECK`, the checking allocator that the tests build with (live-block count, `0xDD` fill, double-free and leak reports), becomes a debug allocator in Tersus that a program or a test selects, and valgrind stays as the second opinion; (d) `fail`, `tersus_overflow` and the exit status become `exit(code)` and `write(fd, ptr, n)` as the only two system calls the language knows by name (`writeByte` and `readByte` of step 20 are the first of them, one byte on the standard output and one from the standard input), and the message is a string constant of step 20; (e) `main` and the printing of the return value become a library function (`fn main_result<T: Display>(x: T)`) that the emitter calls from `@main`. What stays outside Tersus at the end is the part that talks to the system: the entry point and the symbols `alloc`, `realloc`, `free`, `exit` and `write` (an `extern fn` declaration that the emitter turns into an LLVM `declare`, whose contract is an assumption that `tersus assumptions` lists (`POINTERS.md`), linked against libc, or inline assembly for a freestanding build), and the LLVM IR itself. The order is: the derived impls (a), which need only step 26 and not strings; then the allocator and the library `Box` (b, c), which need 25 and 29; then (d) and (e) with step 20; and the test that it is done is that `LlvmRuntime.hs` holds only the declarations of the system functions and `tersus build` needs no C compiler for the runtime, only for the link. `TestNative` and the heap model of `TestOwnership` are the oracle throughout: each piece is moved over while the old C is still there to compare with. Done so far: of (a), drops, copies and printing are code made per type, and no value is walked by a descriptor at run time: the emitter makes a `drop$T` function for each type that owns something, a `print$T` function for each type it holds, and a copy of a value is the `Clone` impl of its type called (a copy the compiler makes for its own reasons is that impl too, which is taken to be a value made of copies of its parts, as the impl for `impl Clone for T { };` is; a copy inside the impl of the type itself is the made `clone$T` function, which copies the words and then what the fields or elements hold, as the runtime's `tersus_clone` did), and the runtime has none of `tersus_drop`, `tersus_clone` or `tersus_print`, and no descriptor tables; of (b): a Box and a list are allocated, grown and freed by the library (`lib/box.tersus` and `lib/lists.tersus`, on `Addr::alloc`, `resize` and `free`, which are `tersus_addr_alloc`, `tersus_addr_resize` and `tersus_addr_free`) and freed by their drops, so the runtime has no Box of its own; `tersus_box_new` is left only for the copies that the made `clone$T` functions make.
31. The lowering from the MIR to LLVM IR written in Tersus
    The plan, with measurements and the slices, is in `STEP31.md`; this is the description it started from.
    The lowering to LLVM IR turns the owned MIR into the text of a `.ll` file, and it is the part of the compiler that is closest to being a plain program over a data structure: a tree in, text out. Writing it in Tersus is the first step of the compiler writing itself, and it is a good test of the language because it is large, has no I/O except reading the MIR and writing the IR, and had an oracle (the Haskell emitter it was ported from) to differ against while it was written. What it needs from the language, so what has to be done first: strings and a growable text buffer, and input and output of text (step 20); enums with data for the MIR (`Program`, `Function`, `BasicBlock`, `Statement`, `Rvalue`, `Type` are all enums and structs, which the language has) and `match` over them, which it has; a map from names and locals to numbers and to types (an ordered map or a hash map as a library over `List` and the traits of steps 22 and 24; today only lists and arrays exist); lists of lists and of structs that own lists (done); recursion over trees (done, with `Box`); and a validator that is fast enough to prove a program of this size, since every function of it goes through the validator (the symbolic executor in `lib/validation/validation.tersus` is the part likely to need work first, as its reasoning is quadratic in the facts of a path). The MIR has to reach the program as data: either `tersus mir --data` prints it in a stable text form (an S-expression, or the `Pretty` form made parseable) that the Tersus emitter reads, or the Haskell side is kept for the front end and hands the MIR over as a value of the same types, which is the later form once the front end is also in Tersus. The steps: (a) fix the serialization of the MIR and a reader and writer of it on both sides, with a test that `read . print = id` for every example (done: `MirData`, `tersus mir --data`, `TestMirData` for the Haskell side, and `lib/mir/mir_reader/mir_reader.tersus`, the types of the MIR and a reader and writer in Tersus that read the data of every example, itself included, and write it again, `TestMirReader`; (b) is begun: `lib/mir/emit/emit.tersus` has the declarations, the descriptors of the types and the entry point, and the code of the functions that make words (operands, arithmetic with its overflow checks, the terminators and calls); 32. Allocators chosen by the code that calls
    The design is `ALLOCATORS.md`. A block `with a { ... }` makes `a` the allocator of what is made inside it, including what the functions it calls make. Where a value's memory comes from is a region in its type (`List<Token, arena>`), which the validator never sees; a region a program leaves out is the context, the region a function is called in (`System` at the top), decided at each call by unification; a borrow and `=` ignore regions, so `clone` copies into the region it is expected in; the context decides only where a value is made, and a value is grown and freed by the region in its type; and a value made in a local allocator cannot leave its `with` block, which drops it at every exit. Natively no container holds an allocator: a region is a hidden `&K` parameter, nothing for `System`, `MirMono` copies a function per kind of allocator and not per block, and a program that uses only `System` compiles to the IR of today. The library has `System`, `Arena`, `Checked` (the `TERSUS_CHECK` of step 30 (c) in Tersus) and `Fixed<n>`. It needs steps 25, 26, 29 and 30 (a)
33. Replacing all Haskell with a fully Tersus native implementation
    The current survey and priorities are in `REPLACING_HASKELL.md` (the pinned pre-replacement survey). The emitter, validator, MIR checker/eraser, parser, ownership, reference-write expansion, elaboration and package resolution are Tersus (a single file's parse still selects its libraries in Haskell). Native monomorphization remains Haskell; the host and tests move alongside it. Reference-write expansion runs before list lowering; the Haskell monomorphization adapter runs before Tersus ownership. See Ownership host above for the transport and cold boundary.
34. What equality in proofs means
    `=` in a proof is the validator's equality: structural, total over every type whether it implements Eq or not, and the meaning of `Eq::eq`'s contract (`return = (self = other)`), which is why an impl cannot compare in its own way (LANGUAGE.md, Equality). To revisit: whether a type that wants a coarser equality (a set kept as a list in any order, a value with a cache) should have `=` in its proofs mean its own Eq, whether `=` in a proof should be refused for a type without Eq, and how either would sit with the validator's congruence (equal arguments give equal results), which a coarser equality does not have for every function
18. Validate calls of function values
    The validator does not follow a call of a function that is a value: `fn apply(g: fn(Int) -> Int, n: Int) -> Int { return g(g(n)); }` is refused with `Function object not validated`, though the type checker, the executor and native code run it. The tests of native code for function values lower the programs without validating them (`functionPrograms` in `TestNative`) because of this
    The function a call reaches is not known statically, so the call needs the contract of the function type (the contracts of a parameter that is a function would be written in its type), or the callee has to be one of a known few
20. Strings, and input and output
    Done: strings (LANGUAGE.md, Strings; a literal can be written in a proof, and `concat` promises its bytes), output (Output, with `writeError` for the standard error), input from the standard input (Input), the command-line arguments (Arguments) and files (Files). A literal is a `String` of UTF-8 bytes, a library struct over a `List<Byte>` (`lib/string.tersus`) that implements `Sequence<Byte>` and `Growable<Byte>` and has `concat`, the readers and writers, so native code and the validator needed nothing new for strings. Everything that touches the world is a few primitives that are `ListOp`s of the MIR: `writeByte` and `writeError`, `readByte`, `argCount` and `argByte`, and `pathByte`, `fileLoad`, `fileByte`, `storeByte` and `fileStore` (a path is built a byte at a time and a whole file is loaded or stored), with the C runtime calling `putchar`, `getchar`, `argv` and `fopen`, and the interpreter threading the input, the path and the files through its monad (`MirEval.runProgramEnv`: `RunEnv` is what it is run in, `Outcome` what it did, including the files written, which the CLI writes when the program has ended). The validator knows only the range of what the reading ones give (`Mir.readersOfInput`, `FnInfo.fnReads`: a function that reads is not a function of its arguments, and a proof may not call one). The type `Byte` (LANGUAGE.md, Bytes: `TByte`, `toByte(x)` and `toInt(b)`, the range of every `Byte` known to the validator) is what a string is made of, and a number written out is a `Byte` where one is wanted (`coerce` in `lib/elaborate/`). What is left of the step, each a design of its own: what the later bytes of a `concat` are without naming the element (the engine does not match `size(a) + j` with a constant index, and a `forall` over a range that is not `0..n` was not preserved by `push`), printing a returned `String` as text, appending to a file, streams and directories, the environment, `write(fd, ptr, n)` and `read` as the only system calls (step 30), and what the validator says of an effect (today it says nothing: a program that fails does not take back what it wrote, the proofs cannot mention what was written or read, and two reads are two unrelated values)
23. Sizes, `Box`, and the data model without implicit heap values (the plan for arrays; DATA_MODEL.md, Sizes and Box)
    `Array<T, N>` (LANGUAGE.md, Arrays) is held inline with a constant size, and holds any value that has a size. The design agreed for the rest: a type has *size parameters* (`Array<T, n>`, and a user type may declare one, `struct Packet<T, n: Int> { ... }`), each a constant, a variable of generic code, or `?` (which may be left out: `Array<T>` is `Array<T, ?>`). A type with a `?` is unsized and is only used behind a pointer, and a pointer to a type carries the values of its `?` parameters in hidden words: `Box<Array<T>>` is a pointer and a length, `Box<Array<T, 3>>` a thin pointer. `Box<T>` is the owning handle (heap ownership is not in `Array`), `&T` a borrowed one later. A pointer to `S<c>` converts to a pointer to `S<?>` by storing the constant in the hidden word. A struct or an enum is an ordinary inline value of the words of its fields (an enum a tag and its largest variant), copied by value, and a recursive type holds its recursion in a `Box`; a list stays the one implicitly heap-allocated type until it is rebuilt as a struct of a `Box<Array<T>>` and a count. The steps, in order:
    1. Size arguments in types, with `?` and its omission (done: `TArrayOf element Size`; an unsized array is refused as a value, and is used behind a `Box`)
    2. Words per type: structs, enums and arrays inline wherever they are made and as fields and list elements, and ownership that asks "does it need to be dropped" and not "is it on the heap" (done: `slotsOf` gives the words of a type; a struct is its fields' words and an enum a tag word and the widest variant, held in the frame, in a field or in a list and copied by value; `needsDrop` says which values own a list or a `Box`, which are then moved, copied and dropped like a list was, with the words cleared when moved from; the runtime walks every value by its descriptor and the words in place)
    3. Thin `Box<T>` with explicit allocation (`Box::new`), transparent to field reads, `match` and the builtins on arrays, and the check that a recursive type has a `Box` in its recursion (done for structs and enums: `TBox`, `Box::new`, `Box::unbox`, `MakeBox` and `Unbox` in the MIR, `checkFinite`; a Box is transparent in values, and natively it is a pointer to room on the heap for the words of what it holds; a Box of any other sized type and the builtins on a Box of an array came with step 4)
    4. Unsized types: `?` behind a pointer, the hidden words, `Array::boxed(n, x)` for a size known only when the program runs, and the unsizing conversion (done: `Box<T>` holds any type that has a size; `Box<Array<T, ?>>` carries its length (in native code it is a `StdList`, the address, the length and the room, freed by its drop); `Array::boxed`, the `Unsize` rvalue that the checker writes where a `Box<Array<T, N>>` is given to a `Box<Array<T>>`, and `size`, `get`, `first`, `last` and `set` looking through a Box of an array)
    5. Size parameters for functions and user types: `fn dot<n>(a: Array<Int, n>, b: Array<Int, n>)` validated once with a symbolic `n` and compiled once per constant, and `struct Packet<T, n: Int>` that is fat behind a `Box` for free (a size parameter may be `?` only in the last field, so the offsets before it are constants). Done for functions (`Size` has `SizeParam`, the checker's own unknown `SizeVar`, and a function with sizes has the type `TForall`; a call instantiates the sizes by unification and writes them as its last arguments; `fnSizeParams` marks them in the MIR; `MirMono` makes a copy per list of constants for native code); user types: a struct with sizes (`struct Packet<n>`) is a struct of its own for each list of sizes, which the type carries structurally (`TNamed` with its `Arg`s; `instanceName` renders one only where a name is needed, and nothing reads a name back; the checker declares one the first time it is looked at, `TcState.tcGenerics` has the declarations, `Mir.completeInstances` declares those the program mentions, and `MirMono` renames them with the sizes put in); enums, impls, `?` and type parameters wait
    6. Borrowed `&T`, for parameters only, so a read-only function costs no copy (done: `TRef`, which only a parameter of a function has, is its type in the function and cannot be assigned there; `fnBorrowed` marks the parameters in the MIR, the ownership pass lends them without a move or a clone and clones what the function takes of one, and native code reads the caller's words where they are)
    7. `List<T>` rebuilt on `Box<Array<T>>`, with `first`, `last`, `get` and `set` as functions of a trait that arrays and lists implement instead of the overload of the checker. In order: (a) arrays of any element type (done: `arrayElement`; an element that owns something is cloned into each slot by `array(n, x)`, dropped when `set` replaces it, and moved, cloned and freed with the array; a literal `#[...]` is still Int, Bool and arrays of them), (b) type parameters for functions and structs, monomorphized like the sizes (done for functions and structs: `TParam`, a capital name between the `<>` of a `fn`, `TForall` with the sizes and the types, `Signature` and `Function.fnTypeParams`; the checker instantiates them with new unknowns that the arguments decide, and `MirMono` makes a copy for each list of types by matching the types of the parameters with those of the arguments and of the result; a struct with types and sizes is a struct of its own for each list of them, which the type carries structurally (`Arg` in `TNamed`; `instanceName` renders a name only where one is needed), so `Vec<List<Int>, 3>` is declared like `Packet<4>` and renamed by `MirMono` in each copy), (c) the rebuilt list and the trait (done: `Vec<T>` and the traits `Sequence<E>` and `Growable<E>` as a library, see LANGUAGE.md, and one function over any of them with a bound, step 21; and the list of native code is a library struct: `lib/lists.tersus` defines `StdList<T>` (a `Box<Array<T>>` and a count, with an invariant) and `stdListNew`/`stdListPush`/`stdListSet`, validated on its own with the contracts of a list (`get` gives what `set` put, `push` adds one and keeps the others), and `MirLists.lowerLists` puts it in the place of every `List<T>` of a validated program before ownership, monomorphization and the emitter, which no longer have lists (the C runtime has no list, only a struct named `StdList` that it prints and compares as one). What it took: `functions in contracts`, `struct invariants`, `traits with types`, `impl<T>`, the prelude (which keeps the traits `Sequence` and `Growable`; `Vec` is the example `examples/vec.tersus`, and a list has its methods and `pop`), `Array::empty()` (an array of no elements, so an empty list needs no element) and reading an element out of a `StdList` where it is, so the part-that-is-only-read optimization is kept. What is not changed: the checker, the validator, the proof engine and the executor still know the builtin `List<T>` (its facts and its `size`, `get`, `set`, `push`, `first` and `last` as overloads), so the proofs about lists are as they were; moving them to the `Sequence` trait means giving the trait the `forall` facts of lists and making the proof engine instantiate them for calls of the trait's functions, which is the part that remains)
